# 企业入驻校验方案：策略模式 + 配置化引擎

> 智园通智慧园区管理平台 · 企业入驻模块设计方案
> 基于实习项目实践的方案总结与面试准备材料

---

## 一、业务背景与需求分析

### 1.1 业务场景

智园通智慧园区管理平台面向多种企业类型提供在线入驻服务，包括但不限于：

| 企业类型 | 典型校验步骤 |
|---------|-------------|
| 科技研发类 | 营业执照 → 法人信息 → 黑名单检查 |
| 金融类 | 营业执照 → 法人信息 → 金融许可证 → 黑名单检查 |
| 外资企业 | 营业执照 → 法人信息 → 涉外资质 → 黑名单检查 |

不同企业类型的校验流程存在差异，且校验以**分步页面**形式呈现，用户需逐步完成每一项校验。

### 1.2 核心需求

| # | 需求 | 说明 |
|---|------|------|
| 1 | **步骤可配置** | 不同企业类型拥有不同的校验步骤序列，通过数据库配置而非硬编码实现 |
| 2 | **步骤可插拔** | 新增/删除校验项时，仅需实现对应逻辑，不修改流程代码 |
| 3 | **分步交互** | 引擎每次只执行当前步骤，等待用户主动提交，而非自动传递到下一步 |
| 4 | **回退能力** | 支持用户回退到之前的步骤重新填写，后续步骤自动重置 |
| 5 | **配置一致性** | 管理员修改校验配置后，进行中的用户流程不受影响 |
| 6 | **并发安全** | 防止用户重复提交（如双击按钮、网络重发） |
| 7 | **高性能** | 避免 N+1 查询，减少数据库压力 |

### 1.3 原实现痛点

原实现将所有校验逻辑硬编码在 Service 层的 if-else 中：

- 每新增一个校验项需修改 **3~5 个文件**
- 圈复杂度超过 20，新人接手困难
- 校验步骤调整需要后端开发介入
- 缺乏并发控制和配置隔离机制

## 二、设计模式选型与对比

### 2.1 候选方案评估

| 方案 | 核心思路 | 适配度 | 优点 | 缺点 |
|------|---------|-------|------|------|
| **A. 纯责任链** | 每个步骤一个节点，链表结构，自动传递 | ⭐⭐⭐ | 语义贴合"链式校验" | 自动传递机制与"分步提交"冲突；快照版本+禁用校验项=死锁；链表索引 O(n) |
| **B. 模板方法** | 抽象类定义固定流程骨架 | ⭐⭐ | 流程骨架固定 | 灵活性不足，步骤序列硬编码在模板中 |
| **C. 状态机** | 每个步骤一个状态，状态间显式转换 | ⭐⭐⭐ | 状态转换清晰 | 步骤数增加时状态爆炸；过度设计 |
| **D. 策略模式 + 配置化引擎** | 每个校验项=策略，引擎按配置调度 | ⭐⭐⭐⭐⭐ | 无明显缺陷 | — |

### 2.2 选型理由

**策略模式 + 配置化引擎** 是最优解，原因如下：

1. **策略模式**天然实现"每个校验项独立、可插拔"——每个策略只关心自己的校验逻辑，互不依赖
2. **配置化引擎**天然支持"步骤序列可配置、分步交互"——引擎根据数据库配置动态组装步骤序列，每次只调度当前步骤的策略
3. 两者配合刚好覆盖所有需求，没有多余的复杂度

### 2.3 与其他方案的关键区别

| 维度 | 责任链方案 | 策略模式 + 引擎方案 |
|------|-----------|-------------------|
| 步骤组织结构 | 链表结构，节点持有 next 引用 | List 结构，引擎按序索引 |
| 步骤查找 | `chain.getNode(stepOrder)` 需遍历 | `strategies.get(stepOrder - 1)` O(1) |
| 分步交互 | 需手动断开自动传递机制 | 天然支持，引擎每次只执行一步 |
| 快照版本 | 需同时放宽 status 校验 | 快照版本直接过滤配置，无额外逻辑 |
| 并发控制 | 无 | 乐观锁 `@Version` |
| N+1 查询 | 每次循环查一次 | 批量查询 + Map 缓存 |
| 回退逻辑 | 链表中删除节点复杂 | List 索引直接定位，批量重置 |

### 3.2 分层职责说明

| 层级 | 类 | 核心职责 |
|------|-----|---------|
| 控制层 | `EnterpriseRegisterController` | HTTP 参数校验、调用 Service、包装响应 |
| 业务层 | `EnterpriseRegisterService` | 业务编排、事务边界控制、异常转换 |
| 引擎层 | `ValidationEngine` | 策略加载（Redis 缓存优先）、步骤调度、前置校验、回退处理 |
| 策略层 | `ValidationStrategy` 各实现类 | 单项校验逻辑（必须无状态，共享状态存 Redis） |
| 缓存层 | `DistributedValidationCache` | Redis 分布式缓存配置，保证集群一致性 |
| 数据层 | Mapper + Entity | 数据库持久化 |

### 3.3 集群设计原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **策略无状态** | 每个 `ValidationStrategy` 实现必须无状态，避免集群不同实例上的状态不一致 |
| 2 | **共享状态放 Redis** | 需要跨实例共享的状态（如 API Token、分布式锁）统一存 Redis |
| 3 | **配置缓存用 Redis** | 校验步骤配置用 Redis 缓存，Key = `validation_config:{typeId}:{version}`，所有实例共享 |
| 4 | **快照版本存数据库** | `config_version` 存 MySQL，天然集群友好，每个实例读同一版本号 |
| 5 | **并发控制用乐观锁** | MyBatis-Plus `@Version` 注解，跨实例安全，比分布式锁更轻量 |
| 6 | **事务边界分离** | 策略执行（无事务，可能耗时）与结果保存（有事务，毫秒级）分离，避免长事务 |

## 四、核心数据模型设计

### 4.1 validation_config（校验步骤配置表）

定义不同企业类型的校验步骤序列，支持配置化驱动。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键，自增 |
| enterprise_type_id | BIGINT | 企业类型 ID（关联 enterprise_type 表） |
| strategy_id | VARCHAR(50) | **业务策略标识符**（如 `BUSINESS_LICENSE`），与 Spring Bean Name 解耦 |
| step_order | INT | 步骤序号（从 1 开始，连续递增） |
| config_version | INT | 配置版本号，由 `enterprise_config_version` 表原子生成 |
| enabled | BOOLEAN | 是否启用，默认 true |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

**配置示例**：

```sql
-- 科技研发类（type_id=1）的校验步骤
INSERT INTO validation_config (enterprise_type_id, strategy_id, step_order, config_version) VALUES
(1, 'BUSINESS_LICENSE',    1, 1),
(1, 'LEGAL_PERSON',        2, 1),
(1, 'BLACKLIST',           3, 1);

-- 金融类（type_id=2）的校验步骤
INSERT INTO validation_config (enterprise_type_id, strategy_id, step_order, config_version) VALUES
(2, 'BUSINESS_LICENSE',    1, 1),
(2, 'LEGAL_PERSON',        2, 1),
(2, 'FINANCIAL_LICENSE',   3, 1),
(2, 'BLACKLIST',           4, 1);
```

**索引设计**：

```sql
-- 高频查询：按企业类型+版本号加载配置
CREATE INDEX idx_config_type_version ON validation_config (enterprise_type_id, config_version);
-- 策略标识符查询
CREATE INDEX idx_config_strategy ON validation_config (strategy_id);
```

### 4.2 enterprise_config_version（配置版本号管理表）

独立管理各企业类型的配置版本号，支持原子自增。版本号生成与配置数据操作解耦，避免高并发下版本号跳变。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键，自增 |
| type_id | BIGINT | 企业类型 ID（唯一索引） |
| current_version | INT | 当前版本号，默认 0 |
| updated_at | DATETIME | 更新时间（自动维护） |

```sql
CREATE TABLE enterprise_config_version (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    type_id         BIGINT       NOT NULL COMMENT '企业类型 ID',
    current_version INT          NOT NULL DEFAULT 0 COMMENT '当前版本号',
    updated_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    UNIQUE KEY uk_type_id (type_id)
) COMMENT '企业校验配置版本号管理表';
```

**索引设计**：已有唯一索引 `uk_type_id (type_id)`，用于原子操作和快速查询。

### 4.3 enterprise_register（入驻申请表）

记录用户的入驻流程状态，包含配置版本快照和过期时间。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键，自增 |
| enterprise_name | VARCHAR(200) | 企业名称 |
| unified_code | VARCHAR(50) | 统一社会信用代码 |
| type_id | BIGINT | 企业类型 ID |
| current_step | INT | 当前步骤序号 |
| config_version | INT | **入驻开始时锁定的配置版本（快照）**，从 `enterprise_config_version` 表读取 |
| status | VARCHAR(20) | 状态：DRAFT / CHECKING / ALL_CHECKED / PENDING_REVIEW / APPROVED / REJECTED / EXPIRED |
| expire_at | DATETIME | **申请过期时间**，创建时设置为当前时间+30天，过期后状态自动更新为EXPIRED |
| version | INT | 乐观锁版本号（MyBatis-Plus @Version） |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

> **关键设计**：
> 1. `config_version` 用于解决"进行中的流程如何应对配置变更"的边界问题。用户开始入驻时，系统记录当前 `validation_config` 表的配置版本号，后续所有校验都以此版本号为准构建链，确保同一用户的校验链在整个入驻过程中保持一致。
> 2. `expire_at` 用于清理僵尸请求。入驻流程有生命周期限制，超过过期时间的申请将被标记为 `EXPIRED` 状态，无法继续操作。

**索引设计**：

```sql
-- 按类型查询入驻记录（高频）
CREATE INDEX idx_register_type ON enterprise_register (type_id);
-- 按状态查询（审核列表、统计等）
CREATE INDEX idx_register_status ON enterprise_register (status);
-- 僵尸请求清理（定时任务使用）
CREATE INDEX idx_register_expire_status ON enterprise_register (expire_at, status);
```

### 4.4 enterprise_check_record（校验记录表）

记录每个步骤的校验结果，支持回退和进度查询。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT | 主键，自增 |
| register_id | BIGINT | 入驻申请 ID（外键） |
| step_order | INT | 步骤序号 |
| strategy_id | VARCHAR(50) | 业务策略标识符（如 `BUSINESS_LICENSE`） |
| status | VARCHAR(20) | 状态：PENDING / PASSED / FAILED |
| form_data | JSON | 用户提交的表单数据 |
| check_result | JSON | 校验结果详情（通过时存通过详情，失败时存错误详情） |
| error_code | VARCHAR(50) | 错误码，独立字段便于按错误码统计分析 |
| error_message | VARCHAR(500) | 错误描述（人类可读） |
| operator_id | BIGINT | 操作人 ID |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

**索引设计**：

```sql
-- 按入驻申请ID批量查询步骤记录（高频，getProgress 使用）
CREATE INDEX idx_record_register ON enterprise_check_record (register_id);
-- 按入驻申请+步骤序号查询（步骤跳转使用）
CREATE INDEX idx_record_register_step ON enterprise_check_record (register_id, step_order);
```

### 4.6 Mapper 接口定义（MyBatis-Plus）

```java
/**
 * 校验配置 Mapper
 */
public interface ValidationConfigMapper extends BaseMapper<ValidationConfig> {

    /**
     * 按企业类型 + 版本号查询全部启用的配置
     * 引擎加载策略列表时使用，支持快照版本隔离
     */
    List<ValidationConfig> selectByTypeAndVersion(
        @Param("typeId") Long typeId,
        @Param("configVersion") Integer configVersion);

    /**
     * 查询所有启用的配置（用于启动时策略一致性预校验）

    List<ValidationConfig> selectAllEnabled();

    /**
     * 按企业类型 + 版本号 + 序号查询单条配置
     * 引擎按序号定位策略时使用
     */
    ValidationConfig selectByTypeAndStep(
        @Param("typeId") Long typeId,
        @Param("configVersion") Integer configVersion,
        @Param("stepOrder") Integer stepOrder);
}

 * 配置版本号 Mapper
 * 版本号原子管理，使用 INSERT ... ON DUPLICATE KEY UPDATE
 */
public interface EnterpriseConfigVersionMapper extends BaseMapper<EnterpriseConfigVersion> {
```

### 5.6 Redis 分布式缓存（集群核心组件）

```java
/**
 * 基于 Redis 的分布式配置缓存
 * 使用 StringRedisTemplate + Jackson JSON 序列化
 * 保证集群所有实例共享同一份配置缓存
 * Key: validation_config:{typeId}:{configVersion}
 * TTL: 30 分钟
 */
@Component
public class DistributedValidationCache {

    private final StringRedisTemplate stringRedisTemplate;
    private final ValidationConfigMapper configMapper;

    /** 空值标记（防止缓存穿透） */
    private static final String EMPTY_MARKER = "EMPTY";

    /** Jackson ObjectMapper，预配置支持 Java 8 时间类型 */
    private static final ObjectMapper OBJECT_MAPPER = new ObjectMapper()
        .registerModule(new JavaTimeModule())
        .registerModule(new Jdk8Module())
        .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);

    public DistributedValidationCache(
            StringRedisTemplate stringRedisTemplate,
            ValidationConfigMapper configMapper) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.configMapper = configMapper;
    }

    /**
     * 加载配置（优先 Redis 缓存，缓存未命中查库）
     * 集群环境下所有实例共享 Redis 缓存
     * 支持空值缓存防止穿透
     */
    public List<ValidationConfig> getConfigs(Long typeId, Integer configVersion) {
        String key = "validation_config:" + typeId + ":" + configVersion;

        // 1. 尝试从 Redis 缓存获取（JSON 格式，可读性好）
        String cachedJson = stringRedisTemplate.opsForValue().get(key);

        // 1a. 命中空值标记（防止缓存穿透）
        if (EMPTY_MARKER.equals(cachedJson)) {
            return Collections.emptyList();
        }

        // 1b. 命中有效缓存
        if (cachedJson != null) {
            try {
                return OBJECT_MAPPER.readValue(
                    cachedJson,
                    new TypeReference<List<ValidationConfig>>() {}
                );
            } catch (Exception e) {
                log.warn("Redis 缓存反序列化失败，回源查库, key={}", key, e);
                stringRedisTemplate.delete(key);
            }
        }

        // 2. 缓存未命中，查库
        List<ValidationConfig> dbConfigs =
            configMapper.selectByTypeAndVersion(typeId, configVersion);

        // 3. 写入缓存（含空值缓存，防止穿透）
        try {
            if (dbConfigs.isEmpty()) {
                stringRedisTemplate.opsForValue()
                    .set(key, EMPTY_MARKER, 1, TimeUnit.MINUTES);
            } else {
                String json = OBJECT_MAPPER.writeValueAsString(dbConfigs);
                stringRedisTemplate.opsForValue()
                    .set(key, json, 30, TimeUnit.MINUTES);
            }
        } catch (Exception e) {
            log.warn("Redis 缓存写入失败, key={}", key, e);
        }

        return dbConfigs;
    }

    /**
     * 清除指定版本的缓存
     */
    public void evictCache(Long typeId, Integer configVersion) {
        stringRedisTemplate.delete("validation_config:" + typeId + ":" + configVersion);
    }

    /**
     * 清除某类型所有版本的缓存（配置全量变更时调用）
     * 使用 SCAN 非阻塞迭代，避免 KEYS 命令阻塞 Redis 主线程
     * 管理员修改配置时只需删除 Redis Key，所有实例下次加载自动重建缓存
     */
    public void evictAllCache(Long typeId) {
        String pattern = "validation_config:" + typeId + ":*";
        Set<String> keys = new HashSet<>();

        stringRedisTemplate.execute((RedisCallback<Void>) connection -> {
            ScanOptions options = ScanOptions.scanOptions().match(pattern).count(100).build();
            try (Cursor<byte[]> cursor = connection.scan(options)) {
                while (cursor.hasNext()) {
                    keys.add(new String(cursor.next(), StandardCharsets.UTF_8));
                }
            }
            return null;
        });

        if (!keys.isEmpty()) {
            stringRedisTemplate.delete(keys);
        }
    }
}
```

### 5.8 ConfigVersionService（配置版本号管理服务）

```java
/**
 * 配置版本号管理服务
 * 负责版本号的原子生成与缓存
 * 版本号生成与配置数据操作解耦，避免高并发下版本号跳变
 */
@Service
public class ConfigVersionService {

    private final EnterpriseConfigVersionMapper versionMapper;
    private final StringRedisTemplate redisTemplate;

    private static final String VERSION_KEY_PREFIX = "config:version:";

    public ConfigVersionService(EnterpriseConfigVersionMapper versionMapper,
                                 StringRedisTemplate redisTemplate) {
        this.versionMapper = versionMapper;
        this.redisTemplate = redisTemplate;
    }

    /**
     * 原子获取下一个版本号（配置变更时调用，写操作）
     * 使用 INSERT ... ON DUPLICATE KEY UPDATE 保证原子性
     *
     * @param typeId 企业类型 ID
     * @return 新版本号
     */
    @Transactional
    public int nextVersion(Long typeId) {
        int rows = versionMapper.insertOrIncrement(typeId);
        if (rows == 0) {
            throw new ValidationException("版本号生成失败，typeId=" + typeId);
        }

        EnterpriseConfigVersion version = versionMapper.selectByTypeId(typeId);
        int newVersion = version.getCurrentVersion();

        // 同步到 Redis 缓存
        redisTemplate.opsForValue().set(
            VERSION_KEY_PREFIX + typeId,
            String.valueOf(newVersion),
            1, TimeUnit.HOURS
        );
        return newVersion;
    }

    /**
     * 获取当前版本号（入驻时调用，读操作，不加锁）
     * 优先 Redis，缓存未命中查库
     *
     * @param typeId 企业类型 ID
     * @return 当前版本号
     */
    public int currentVersion(Long typeId) {
        String redisKey = VERSION_KEY_PREFIX + typeId;

        String cached = redisTemplate.opsForValue().get(redisKey);
        if (cached != null) {
            return Integer.parseInt(cached);
        }

        EnterpriseConfigVersion version = versionMapper.selectByTypeId(typeId);
        if (version == null) {
            return 0;
        }

        redisTemplate.opsForValue().set(redisKey,
            String.valueOf(version.getCurrentVersion()), 1, TimeUnit.HOURS);
        return version.getCurrentVersion();
    }

    /**
     * 设置版本号（配置回滚时使用）
     * 直接更新 current_version 并同步 Redis 缓存
     *
     * @param typeId       企业类型 ID
     * @param newVersion   目标版本号
     */
    @Transactional
    public void setVersion(Long typeId, int newVersion) {
        int rows = versionMapper.updateVersion(typeId, newVersion);
        if (rows == 0) {
            throw new ValidationException("版本号更新失败，typeId=" + typeId);
        }
        // 同步到 Redis 缓存
        redisTemplate.opsForValue().set(
            VERSION_KEY_PREFIX + typeId,
            String.valueOf(newVersion),
            1, TimeUnit.HOURS
        );
    }
```

### 5.9 ValidationEngine（执行引擎）

```java
/**
 * 校验执行引擎
 * 负责：策略加载、步骤调度、前置校验、回退处理
 */
@Service
public class ValidationEngine {

    private final DistributedValidationCache cache;
    private final EnterpriseCheckRecordMapper recordMapper;
    private final Map<String, ValidationStrategy> strategyMap;

    /**
     * 通过 Spring 自动注入所有 ValidationStrategy 实现
     * 注入分布式缓存（Redis）保证集群一致性
     * 使用 getIdentifier()（业务标识）而非 Bean Name 作为 Key
     * 启动时预校验：确保数据库 strategy_id 与代码策略映射一致（Fail-Fast）
     */
    public ValidationEngine(List<ValidationStrategy> strategies,
                            DistributedValidationCache cache,
                            EnterpriseCheckRecordMapper recordMapper,
                            ValidationConfigMapper configMapper) {
        this.cache = cache;
        this.recordMapper = recordMapper;
        this.strategyMap = strategies.stream()
            .collect(Collectors.toMap(
                ValidationStrategy::getIdentifier,
                Function.identity()
            ));

        // 启动时预校验（详见 5.10 节）
        List<ValidationConfig> allConfigs = configMapper.selectAllEnabled();
        Set<String> dbStrategyIds = allConfigs.stream()
            .map(ValidationConfig::getStrategyId)
            .collect(Collectors.toSet());
        List<String> missingIds = dbStrategyIds.stream()
            .filter(id -> !this.strategyMap.containsKey(id))
            .toList();
        if (!missingIds.isEmpty()) {
            throw new IllegalStateException(
                "数据库中存在未注册的策略标识符：" + missingIds);
        }
    }

    /**
     * 按类型+版本加载策略列表
     * 集群环境下通过 Redis 缓存保证所有实例获取一致的配置
     *
     * @param typeId        企业类型 ID
     * @param configVersion 配置版本号（快照）
     * @return 按 step_order 排序的策略列表
     */
    public List<ValidationStrategy> loadStrategies(Long typeId, Integer configVersion) {
        // 从 Redis 分布式缓存加载（所有实例共享）
        List<ValidationConfig> configs = cache.getConfigs(typeId, configVersion);

        if (configs.isEmpty()) {
            throw new ValidationException("企业类型未配置校验步骤，typeId=" + typeId);
        }

        // 先过滤启用的配置，再按 step_order 排序
        // 禁用的步骤不参与序号校验和策略装配
        List<ValidationConfig> enabledConfigs = configs.stream()
            .filter(c -> Boolean.TRUE.equals(c.getEnabled()))
            .sorted(Comparator.comparingInt(ValidationConfig::getStepOrder))
            .toList();

        if (enabledConfigs.isEmpty()) {
            throw new ValidationException("该企业类型无启用的校验步骤");
        }

        // 验证序号连续性（仅基于启用的配置）
        for (int i = 0; i < enabledConfigs.size(); i++) {
            int expectedOrder = i + 1;
            if (enabledConfigs.get(i).getStepOrder() != expectedOrder) {
                throw new ValidationException(
                    String.format("步骤序号不连续，期望第%d步，实际第%d步。" +
                        "可能是中间步骤被禁用后未重新排序",
                        expectedOrder, enabledConfigs.get(i).getStepOrder()));
            }
        }

        // 策略映射（用业务标识符 strategy_id 查找，与 Bean Name 解耦）
        List<ValidationStrategy> strategies = enabledConfigs.stream()
            .map(c -> {
                ValidationStrategy s = strategyMap.get(c.getStrategyId());
                if (s == null) {
                    throw new ValidationException(
                        "策略未注册：" + c.getStrategyId() +
                        "，请确认数据库配置与代码实现一致");
                }
                return s;
            })
            .toList();

        return strategies;
    }

    /**
     * 执行指定步骤的校验
     * 不自动传递到下一步，等待用户主动提交
     *
     * @param register  入驻申请（含 configVersion 快照）
     * @param stepOrder 步骤序号
     * @param formData  用户提交的表单数据
     * @param operatorId 操作人 ID
     * @return 执行结果（含校验结果和策略标识符，供 saveCheckResult 使用，避免重复加载配置）
     */
    public StepExecutionResult executeStep(EnterpriseRegister register,
                                        int stepOrder,
                                        Map<String, Object> formData,
                                        Long operatorId) {
        // 1. 用快照版本加载策略（保证一致性）
        List<ValidationStrategy> strategies = loadStrategies(
            register.getTypeId(), register.getConfigVersion());

        // 2. 步骤合法性校验
        if (stepOrder < 1 || stepOrder > strategies.size()) {
            throw new ValidationException(
                String.format("步骤序号越界，当前共%d步，请求第%d步",
                    strategies.size(), stepOrder));
        }

        // 3. 前置步骤必须通过
        if (stepOrder > 1) {
            boolean prevPassed = recordMapper.isStepPassed(
                register.getId(), stepOrder - 1);
            if (!prevPassed) {
                throw new ValidationException(
                    "第" + (stepOrder - 1) + "步未通过，无法提交第" + stepOrder + "步");
            }
        }

        // 4. 当前步骤不能重复提交
        EnterpriseCheckRecord existing = recordMapper.selectByRegisterAndStep(
            register.getId(), stepOrder);
        if (existing != null && "PASSED".equals(existing.getStatus())) {
            throw new ValidationException("第" + stepOrder + "步已通过，无需重复提交");
        }

        // 5. 执行校验（无事务，策略可能调用外部 API）
        ValidationStrategy strategy = strategies.get(stepOrder - 1);
        ValidationContext ctx = new ValidationContext(register, formData, operatorId, stepOrder);
        ValidationResult result = strategy.validate(ctx);

        // 6. 返回富结果：包含校验结果 + 策略标识符 + 总步数，
        //    供 saveCheckResult 直接使用，避免重复加载配置
        return new StepExecutionResult(result, strategy.getIdentifier(), strategies.size());
    }

    /**
     * 回退：将目标步骤之后的所有校验记录重置为 PENDING
     *
     * @param register   入驻申请
     * @param targetStep 目标步骤（回退到此步骤之前的状态）
     */
    @Transactional
    public void rollback(EnterpriseRegister register, int targetStep) {
        // 批量重置后续步骤
        recordMapper.resetStepsAfter(register.getId(), targetStep);
        register.setCurrentStep(targetStep);
        // 乐观锁更新
        registerMapper.updateById(register);
    }

    /**
     * 获取进度信息
     *
     * @param register 入驻申请
     * @return 进度（含每步状态、表单数据等）
     */
    public ProgressVO getProgress(EnterpriseRegister register) {
        List<ValidationStrategy> strategies = loadStrategies(
            register.getTypeId(), register.getConfigVersion());

        List<EnterpriseCheckRecord> records = recordMapper.selectByRegisterId(
            register.getId());

        // 组装进度视图
        List<StepInfoVO> steps = strategies.stream()
            .map(s -> {
                EnterpriseCheckRecord record = records.stream()
                    .filter(r -> r.getStrategyId().equals(s.getIdentifier()))
                    .findFirst()
                    .orElse(null);
                return new StepInfoVO(
                    s.getIdentifier(),
                    s.getDisplayName(),
                    record != null ? record.getStatus() : "PENDING",
                    record != null ? record.getFormData() : null
                );
            })
            .toList();

        return new ProgressVO(register.getCurrentStep(), register.getStatus(), steps);
    }
}
```

### 5.10 策略一致性校验（运行时保护）

数据库中配置的 `strategy_id` 可能与代码中注册的策略标识符不一致（如拼写错误、遗漏实现）。本章提供**两层校验机制**，确保配置与代码始终一致。

#### 第一层：启动时预校验（Fail-Fast）

在 `ValidationEngine` 构造函数中增加校验，应用启动时即检查数据库中所有 `strategy_id` 是否在策略映射中存在。不匹配则启动失败，Fail-Fast。

```java
public ValidationEngine(List<ValidationStrategy> strategies,
                        DistributedValidationCache cache,
                        EnterpriseCheckRecordMapper recordMapper,
                        ValidationConfigMapper configMapper) {
    this.cache = cache;
    this.recordMapper = recordMapper;
    this.strategyMap = strategies.stream()
        .collect(Collectors.toMap(
            ValidationStrategy::getIdentifier,
            Function.identity()
        ));

    // 启动时预校验：检查数据库中所有 strategy_id 是否在策略映射中存在
    // 不匹配则启动失败，Fail-Fast
    List<ValidationConfig> allConfigs = configMapper.selectAllEnabled();
    Set<String> dbStrategyIds = allConfigs.stream()
        .map(ValidationConfig::getStrategyId)
        .collect(Collectors.toSet());

    List<String> missingIds = dbStrategyIds.stream()
        .filter(id -> !strategyMap.containsKey(id))
        .toList();

    if (!missingIds.isEmpty()) {
        throw new IllegalStateException(
            "数据库中存在未注册的策略标识符：" + missingIds +
            "。请确认代码实现与数据库配置一致。"
        );
    }

    log.info("策略映射初始化完成，共加载 {} 个策略，数据库引用 {} 个",
        strategyMap.size(), dbStrategyIds.size());
}
```

#### 第二层：配置变更时校验

在 `ValidationConfigService.updateConfig()` 方法中增加校验，管理员保存配置时实时检查策略标识符的有效性。

```java
@Service
public class ValidationConfigService {

    private final ConfigVersionService versionService;
    private final ValidationConfigMapper configMapper;
    private final DistributedValidationCache cache;
    private final Map<String, ValidationStrategy> strategyMap;  // 注入引擎的策略映射

    /**
     * 修改校验配置
     * 保存前校验 strategy_id 是否在策略映射中存在
     */
    @Transactional
    public int updateConfig(Long typeId, List<ValidationConfig> configs) {
        // 校验 strategy_id 是否在策略映射中存在
        List<String> invalidIds = configs.stream()
            .map(ValidationConfig::getStrategyId)
            .filter(id -> !strategyMap.containsKey(id))
            .toList();

        if (!invalidIds.isEmpty()) {
            throw new ValidationException(
                "无效的策略标识符：" + invalidIds +
                "。有效的标识符为：" + strategyMap.keySet());
        }

        // 原子生成新版本号（ConfigVersionService 独立表 + INSERT ON DUPLICATE KEY UPDATE）
        int newVersion = versionService.nextVersion(typeId);

        // 将新配置以新版本号写入数据库
        for (ValidationConfig config : configs) {
            config.setEnterpriseTypeId(typeId);
            config.setConfigVersion(newVersion);
            configMapper.insert(config);
        }

        // 清理 Redis 缓存
        cache.evictAllCache(typeId);

        return newVersion;
    }
}
```

**校验时机汇总**：

| 时机 | 校验内容 | 失败行为 |
|------|---------|---------|
| 应用启动 | 数据库所有 `strategy_id` vs 代码 `strategyMap` | 启动失败，Fail-Fast |
| 管理员保存配置 | 新配置的 `strategy_id` vs 代码 `strategyMap` | 拒绝保存，提示有效标识符列表 |
| 引擎执行（兜底） | 运行时再校验一次（loadStrategies 中已有） | 执行失败，抛出异常 |

### 5.11 EnterpriseRegisterService（业务服务）

```java
/**
 * 企业入驻业务服务
 * 负责：事务边界控制、异常转换、调用引擎
 */
@Service
public class EnterpriseRegisterService {

    private final ValidationEngine engine;
    private final DistributedValidationCache cache;
    private final ConfigVersionService versionService;
    private final EnterpriseRegisterMapper registerMapper;
    private final EnterpriseCheckRecordMapper recordMapper;

    /**
     * 开始入驻
     * 从 enterprise_config_version 表（通过 ConfigVersionService）读取当前版本号
     * Redis 缓存优先，保证集群所有实例读取一致的版本号
     */
    @Transactional
    public Long startRegister(Long typeId, String enterpriseName,
                               String unifiedCode, Long operatorId) {
        // 1. 从 ConfigVersionService 读取当前版本号（原子操作，Redis+DB 双写）
        int configVersion = versionService.currentVersion(typeId);

        // 2. 创建入驻申请
        EnterpriseRegister register = new EnterpriseRegister();
        register.setTypeId(typeId);
        register.setEnterpriseName(enterpriseName);
        register.setUnifiedCode(unifiedCode);
        register.setCurrentStep(1);
        register.setConfigVersion(configVersion);  // 快照！
        register.setStatus(RegisterStatus.DRAFT.getCode());
        register.setVersion(0);
        registerMapper.insert(register);

        return register.getId();
    }

    /**
     * 提交某步骤的校验
     * 策略执行（无事务）→ 保存结果（有事务）
     * executeStep 返回 StepExecutionResult（含 strategyId），
     * saveCheckResult 直接使用，避免重复调用 loadStrategies
     */
    public CheckResultDTO submitStep(Long registerId, int stepOrder,
                                      Map<String, Object> formData,
                                      Long operatorId) {
        // 1. 查询入驻申请
        EnterpriseRegister register = registerMapper.selectById(registerId);
        if (register == null) {
            throw new ValidationException("入驻申请不存在");
        }

        // 2. 无事务执行业务校验（可能涉及外部调用，耗时较长）
        //    返回富结果 StepExecutionResult，含 strategyId 供后续使用
        StepExecutionResult executionResult = engine.executeStep(
            register, stepOrder, formData, operatorId);

        // 3. 有事务保存结果（仅 DB 操作，直接使用 executionResult 中的 strategyId 和 totalSteps）
        return saveCheckResult(register, stepOrder, formData,
            executionResult.getResult(), executionResult.getStrategyId(),
            executionResult.getTotalSteps(), operatorId);
    }

    /**
     * 保存校验结果（事务方法）
     *
     * @param strategyId  策略标识符，由 executeStep 返回
     * @param totalSteps 总步数，由 executeStep 返回，避免重复加载配置
     */
    @Transactional
    public CheckResultDTO saveCheckResult(EnterpriseRegister register,
                                           int stepOrder,
                                           Map<String, Object> formData,
                                           ValidationResult result,
                                           String strategyId,
                                           int totalSteps,
                                           Long operatorId) {
        // 3a. 保存校验记录
        EnterpriseCheckRecord record = new EnterpriseCheckRecord();
        record.setRegisterId(register.getId());
        record.setStepOrder(stepOrder);
        record.setFormData(formData);
        record.setStrategyId(strategyId);  // 直接使用，无需再次加载配置
        record.setStatus(result.isPassed() ? "PASSED" : "FAILED");
        record.setOperatorId(operatorId);

        if (result.isPassed()) {
            record.setCheckResult(result.getDetails());
            recordMapper.insert(record);
        } else {
            // 失败时：errorCode 和 errorMessage 写入独立字段，便于统计分析
            record.setErrorCode(result.getErrorCode() != null ? result.getErrorCode() : "");
            record.setErrorMessage(result.getMessage());
            record.setCheckResult(result.getDetails());  // 额外错误详情仍存 JSON
            recordMapper.insert(record);
            // 校验失败，不推进步骤；传递 errorCode 供前端定制化交互
            return CheckResultDTO.fail(
                result.getErrorCode() != null ? result.getErrorCode() : "",
                result.getMessage());
        }

        // 3b. 校验通过，推进步骤（totalSteps 由 executeStep 传入，无需再次加载配置）
        if (stepOrder == register.getCurrentStep()) {
            register.setCurrentStep(stepOrder + 1);
        }

        // 3c. 所有步骤完成
        if (stepOrder >= totalSteps) {
            register.setStatus(RegisterStatus.CHECKING.getCode());
        }

        // 3d. 乐观锁更新（防止并发）
        registerMapper.updateById(register);

        return CheckResultDTO.success(result.getMessage());
    }

    /**
     * 回退到指定步骤
     */
    @Transactional
    public void rollbackTo(Long registerId, int targetStep, Long operatorId) {
        EnterpriseRegister register = registerMapper.selectById(registerId);
        if (register == null) {
            throw new ValidationException("入驻申请不存在");
        }

        if (targetStep > register.getCurrentStep()) {
            throw new ValidationException("回退目标步骤不能大于当前步骤");
        }

        engine.rollback(register, targetStep);
    }

    /**
     * 查询进度
     */
    public ProgressVO getProgress(Long registerId) {
        EnterpriseRegister register = registerMapper.selectById(registerId);
        if (register == null) {
            throw new ValidationException("入驻申请不存在");
        }
        return engine.getProgress(register);
    }
}
```

## 七、快照版本号方案详解

### 7.1 问题场景

当管理员在用户入驻过程中修改校验配置时，会出现链路错位问题：

```
T0: 用户开始入驻（科技研发类，链：[营业执照, 法人信息]）
T1: 用户完成第1步（营业执照通过，current_step = 2）
T2: 管理员修改数据库 — 给科技研发类新增"黑名单检查"（step_order=2）
     新链变为 [营业执照, 黑名单检查, 法人信息]
T3: 用户提交第2步 → 取到的是"黑名单检查"而非原来的"法人信息" ❌
```

### 7.2 解决方案

**核心思路**：在入驻开始时通过 `ConfigVersionService` 锁定配置版本（Redis 缓存 + 数据库原子操作），后续始终以此版本构建链。

#### Step 1：独立版本号表 `enterprise_config_version`

版本号生成与配置数据解耦，通过 `INSERT ... ON DUPLICATE KEY UPDATE` 保证原子性，高并发下不会跳版。

```sql
-- 原子自增版本号（配置变更时调用）
INSERT INTO enterprise_config_version (type_id, current_version)
VALUES (#{typeId}, 1)
ON DUPLICATE KEY UPDATE current_version = current_version + 1;
```

#### Step 2：入驻开始时读取当前版本号（只读，Redis 缓存优先）

```java
// ConfigVersionService.currentVersion() 
// 优先 Redis 缓存 → 缓存未命中查库 → 回填 Redis
int configVersion = versionService.currentVersion(typeId);

EnterpriseRegister register = new EnterpriseRegister();
register.setConfigVersion(configVersion);  // 快照！
```

#### Step 3：配置变更时原子生成新版本

```java
// ConfigVersionService.nextVersion()
// 使用 INSERT ... ON DUPLICATE KEY UPDATE 原子自增
int newVersion = versionService.nextVersion(typeId);

// 新版本号写入 validation_config
config.setConfigVersion(newVersion);
configMapper.insert(config);

// 清理 Redis 缓存
cache.evictAllCache(typeId);
```

#### Step 4：引擎使用快照版本加载策略

```java
// 与之前相同，按版本号过滤配置
List<ValidationConfig> configs =
    cache.getConfigs(typeId, configVersion);
```

#### Step 5：版本号隔离说明

```
时间线：
T0: 管理员创建初始配置，nextVersion() → V1（原子自增）
    → validation_config 写入 V1 的配置

T1: 用户 A 开始入驻，currentVersion() → V1（Redis 缓存命中）
    → enterprise_register.config_version = 1（快照）

T2: 管理员修改配置，nextVersion() → V2（原子自增，不会跳版）
    → validation_config 写入 V2 的配置
    → Redis 缓存清除

T3: 用户 A 提交步骤 1 → 用快照 V1 加载配置
T4: 用户 B 开始入驻，currentVersion() → V2
    → enterprise_register.config_version = 2（快照）
    → 用 V2 的配置
```

#### Step 6：禁用的步骤在快照模式下自动跳过

快照版本锁定了配置结构，但如果管理员禁用了某个校验项（`enabled=false`），引擎在加载策略时会自动过滤掉已禁用的步骤，不会影响进行中的流程：

```java
// loadStrategies 中（详见 5.9 节）
List<ValidationConfig> enabledConfigs = configs.stream()
    .filter(c -> Boolean.TRUE.equals(c.getEnabled()))  // 过滤已禁用的步骤
    .sorted(Comparator.comparingInt(ValidationConfig::getStepOrder))
    .toList();
```

**说明**：已禁用的步骤不参与序号校验和策略装配，引擎只加载 `enabled=true` 的步骤。这确保了快照版本的流程在步骤被禁用后仍能正常推进。

### 7.3 效果对比

| 对比维度 | 无版本控制（实时查库） | 快照版本号方案 |
|---------|---------------------|--------------|
| 新配置对新用户 | ✅ 立即生效 | ✅ 立即生效（新用户开始入驻时读最新版本） |
| 新配置对进行中用户 | ❌ 链路错位 | ✅ 不受影响（继续用旧版本） |
| 回退到已完成步骤 | ❌ 可能取到不同的 Handler | ✅ 始终使用同一版本的链 |
| 实现复杂度 | 简单 | 略高（需版本号字段 + 版本过滤查询） |

### 10.3 调整校验顺序

**场景**：金融类需要将"金融许可证校验"调整到第 4 步。

**步骤**：在 `ValidationConfigService`（5.10 节定义）中增加 `reorderSteps` 方法，通过 `ConfigVersionService` 创建新版本，复制旧配置修改 `step_order` 后写入：

```java
    /**
     * 调整校验顺序
     * 复制旧版本配置 → 修改 step_order → 以新版本写入
     * 保证进行中的入驻流程使用旧版本配置，不受变更影响
     *
     * 边界处理：首次配置时（V0→V1），旧版本为空，需使用 initConfig() 初始化
     */
    @Transactional
    public int reorderSteps(Long typeId, List<StepOrderChange> changes) {
        // 1. 原子生成新版本号
        int newVersion = versionService.nextVersion(typeId);

        // 2. 读取旧版本全部配置（含边界处理）
        int prevVersion = versionService.currentVersion(typeId) - 1;
        List<ValidationConfig> oldConfigs = (prevVersion > 0)
            ? configMapper.selectByTypeAndVersion(typeId, prevVersion)
            : Collections.emptyList();

        if (oldConfigs.isEmpty()) {
            throw new ValidationException(
                "首次配置时请使用 initConfig() 方法初始化配置，" +
                "或直接在 validation_config 表插入初始数据");
        }

        // 3. 复制并按变更修改 step_order，写入新版本
        Map<String, Integer> changeMap = changes.stream()
            .collect(Collectors.toMap(
                StepOrderChange::getStrategyId,
                StepOrderChange::getNewStepOrder
            ));

        for (ValidationConfig config : oldConfigs) {
            ValidationConfig copy = new ValidationConfig();
            BeanUtils.copyProperties(config, copy);
            copy.setId(null);
            copy.setConfigVersion(newVersion);
            // 如果该策略在变更列表中，使用新序号
            copy.setStepOrder(changeMap.getOrDefault(
                config.getStrategyId(), config.getStepOrder()));
            configMapper.insert(copy);
        }

        // 4. 清理 Redis 缓存
        cache.evictAllCache(typeId);
        return newVersion;
    }

    /** 步骤序号变更 DTO */
    @Data
    public static class StepOrderChange {
        private String strategyId;
        private Integer newStepOrder;
    }
```

**SQL 方式**（仅用于一次性初始化，不推荐日常使用）：
```sql
-- 注意：直接 UPDATE 会影响正在进行的入驻流程，仅在首次初始化或无进行中流程时使用
UPDATE validation_config SET step_order = 4 
    WHERE enterprise_type_id = 2 AND strategy_id = 'FINANCIAL_LICENSE';
UPDATE validation_config SET step_order = 3 
    WHERE enterprise_type_id = 2 AND strategy_id = 'BLACKLIST';
```

### 10.4 动态启用/禁用校验项

**场景**：暂时禁用"黑名单校验"。

**步骤**：在 `ValidationConfigService`（5.10 节定义）中增加 `toggleConfig` 方法：

```java
    /**
     * 启用/禁用某个校验项
     * 复制旧版本配置 → 修改 enabled → 以新版本写入
     *
     * 边界处理：首次配置时（V0→V1），oldConfigs 为空，直接以新版本写入初始配置
     */
    @Transactional
    public int toggleConfig(Long typeId, String strategyId, boolean enabled) {
        // 1. 原子生成新版本号
        int newVersion = versionService.nextVersion(typeId);

        // 2. 读取旧版本配置
        int prevVersion = versionService.currentVersion(typeId) - 1;
        List<ValidationConfig> oldConfigs = (prevVersion > 0)
            ? configMapper.selectByTypeAndVersion(typeId, prevVersion)
            : Collections.emptyList();  // 首次配置时无旧版本

        if (oldConfigs.isEmpty()) {
            // 边界：首次配置（V0→V1），无法复制旧版本
            // 需要外部传入初始配置列表，此处抛出异常提示
            throw new ValidationException(
                "首次配置时请使用 initConfig() 方法初始化配置，" +
                "或直接在 validation_config 表插入初始数据");
        }

        // 3. 复制并修改，写入新版本
        List<ValidationConfig> newConfigs = oldConfigs.stream()
            .map(c -> {
                ValidationConfig copy = new ValidationConfig();
                BeanUtils.copyProperties(c, copy);
                copy.setId(null);
                copy.setConfigVersion(newVersion);
                copy.setEnabled(c.getStrategyId().equals(strategyId) ? enabled : c.getEnabled());
                return copy;
            })
            .toList();

        for (ValidationConfig config : newConfigs) {
            configMapper.insert(config);
        }

        // 4. 清理 Redis 缓存
        cache.evictAllCache(typeId);
        return newVersion;
    }
```

### 10.5 配置回滚

**场景**：管理员修改了金融类企业的校验配置后发现有误，需要回滚到上一版本。

**步骤**：在 `ValidationConfigService`（5.10 节定义）中增加 `rollbackConfig` 方法，利用快照版本机制天然支持回滚——每个版本的配置是独立存储的，只需将 `enterprise_config_version` 表的 `current_version` 回退一位：

```java
    /**
     * 回滚配置版本
     * 将 current_version 回退到上一版本，新的入驻申请将使用旧版本配置
     * 进行中的入驻申请不受影响（已锁定快照版本）
     */
    @Transactional
    public int rollbackConfig(Long typeId) {
        Integer currentVersion = versionService.currentVersion(typeId);
        if (currentVersion == null || currentVersion <= 1) {
            throw new ValidationException("已是初始版本，无法回滚");
        }

        // 1. 将版本号回退
        int targetVersion = currentVersion - 1;
        versionService.setVersion(typeId, targetVersion);

        // 2. 清理 Redis 缓存，下次加载时读到旧版本
        cache.evictAllCache(typeId);

        log.warn("配置版本已回滚：typeId={}, from V{} to V{}",
            typeId, currentVersion, targetVersion);
        return targetVersion;
    }
```

**回滚影响**：
- ✅ **新入驻申请**：直接使用回滚后的版本配置
- ✅ **进行中申请**：不受影响，继续使用启动时锁定的快照版本
- ✅ **历史记录**：不受影响，已保存的校验记录保持原样

### 10.6 僵尸请求清理（基础规则）

**场景**：用户创建入驻申请后长期未完成（超过30天），`enterprise_register` 表中堆积大量僵尸请求，占用数据库资源且可能导致业务数据混乱。

**解决方案**：采用「被动过期法」，通过「创建时设置过期时间 + 定时任务批量清理 + 核心接口前置校验」三步实现。

#### Step 1：创建申请时设置过期时间

在 `EnterpriseRegisterServiceImpl.startRegister()` 方法中，创建申请时设置 `expireAt` 字段：

```java
@Transactional
public Long startRegister(Long typeId, String enterpriseName,
                           String unifiedCode, Long operatorId) {
    int configVersion = versionService.currentVersion(typeId);

    EnterpriseRegister register = new EnterpriseRegister();
    register.setTypeId(typeId);
    register.setEnterpriseName(enterpriseName);
    register.setUnifiedCode(unifiedCode);
    register.setCurrentStep(1);
    register.setConfigVersion(configVersion);
    register.setStatus(RegisterStatus.DRAFT.getCode());
    register.setVersion(0);
    // 新增：设置过期时间为当前时间+30天
    register.setExpireAt(LocalDateTime.now().plusDays(30));
    registerMapper.insert(register);

    return register.getId();
}
```

#### Step 2：定时任务批量清理过期申请

每小时扫描一次，将超过过期时间且仍为「校验中/校验完成」状态的申请标记为 `EXPIRED`：

```java
@Component
@Slf4j
public class RegisterCleanupTask {

    private final EnterpriseRegisterMapper registerMapper;
    private final EnterpriseCheckRecordMapper recordMapper;

    /**
     * 每小时执行一次，清理过期的入驻申请
     * 仅处理「校验中/校验完成」状态的申请，排除审核中、终态申请
     */
    @Scheduled(cron = "0 0 * * * ?")  // 每小时整点执行
    @Transactional
    public void cleanExpiredRegisters() {
        LocalDateTime now = LocalDateTime.now();

        // 1. 查询已过期且仍为进行中状态的申请
        List<EnterpriseRegister> expiredList = registerMapper.selectList(
            new QueryWrapper<EnterpriseRegister>()
                .lt("expire_at", now)
                .in("status", 
                    RegisterStatus.DRAFT.getCode(),
                    RegisterStatus.CHECKING.getCode(),
                    RegisterStatus.ALL_CHECKED.getCode()
                )
        );

        if (expiredList.isEmpty()) {
            return;
        }

        // 2. 批量更新为EXPIRED状态（保留数据以供审计追溯）
        for (EnterpriseRegister register : expiredList) {
            register.setStatus(RegisterStatus.EXPIRED.getCode());
            registerMapper.updateById(register);
        }

        log.info("清理过期入驻申请：共 {} 条，状态已更新为 EXPIRED", expiredList.size());
    }
}
```

**边界处理**：
- ✅ **排除审核中申请**：`PENDING_REVIEW` 状态的申请（已完成校验，等待人工审核）不参与清理，因为流程已完成
- ✅ **排除终态申请**：`APPROVED`/`REJECTED` 状态的申请无需清理
- ✅ **保留数据**：仅更新状态为 `EXPIRED`，不物理删除，保留数据以供审计

#### Step 3：核心接口前置校验

在所有涉及入驻操作的接口开头，增加过期状态校验，阻断过期申请的继续操作：

```java
@Service
public class EnterpriseRegisterServiceImpl implements EnterpriseRegisterService {

    // submitStep、getProgress、rollbackTo 等方法的开头都需要添加校验
    public CheckResultDTO submitStep(Long registerId, int stepOrder, ...) {
        EnterpriseRegister register = registerMapper.selectById(registerId);
        if (register == null) {
            throw new ValidationException("入驻申请不存在");
        }

        // 新增：过期状态校验
        if (RegisterStatus.EXPIRED.getCode().equals(register.getStatus())) {
            throw new ValidationException("您的入驻申请已过期，请重新发起入驻申请");
        }

        // 后续原有逻辑...
    }
}
```

需要添加过期校验的方法：
- `submitStep`：提交校验步骤
- `getProgress`：查询进度
- `rollbackTo`：回退步骤
- 其他任何需要操作 `enterprise_register` 的方法

在 `RegisterStatus` 枚举中增加 `EXPIRED` 状态：

|------|------|

## 十一、集群部署挑战与优化方案

### 11.1 集群环境下的核心问题

| # | 问题 | 风险等级 | 影响 |
|---|------|---------|------|
| 1 | **本地缓存不一致** | 🔴 高 | 各实例持有独立的本地缓存，配置变更时部分实例仍用旧缓存 |
| 2 | **策略 Bean 有状态** | 🔴 高 | 不同实例上的 Bean 状态可能不同步（如缓存的外部 API Token） |
| 3 | **配置变更通知** | 🟡 中 | 管理员修改配置后，需通知所有实例刷新缓存 |
| 4 | **并发提交** | 🟡 中 | 不同实例可能同时处理同一用户的请求 |
| 5 | **异步回调路由** | 🟡 中 | 审核回调可能打到非原始处理实例 |
| 6 | **分布式事务** | 🟢 低 | 跨实例数据一致性（当前设计已正确处理） |

### 11.2 优化方案

#### 方案 1：Redis 分布式缓存（解决问题 1）

将本地 `ConcurrentHashMap` 缓存替换为 Redis 缓存，所有实例共享同一份缓存。详见 [第五章 5.6 节](#56-redis-分布式缓存集群核心组件)。

**缓存 Key 设计**：
```
validation_config:{typeId}:{configVersion}
```
- `typeId`：企业类型 ID
- `configVersion`：配置版本号（快照）
- TTL：30 分钟（入驻是低频操作，足够使用）

**配置变更时的缓存失效策略**：管理员修改配置后，通过删除 Redis Key 实现所有实例的缓存失效。新用户入驻时读新版本，老用户用快照版本不受影响。`ValidationConfigService`（5.10 节定义）中 `updateConfig()` 方法的核心逻辑：

```java
    @Transactional
    public void updateConfig(Long typeId, ...) {
        int newVersion = versionService.nextVersion(typeId);  // 原子生成新版本号
        configMapper.insertWithVersion(newVersion, ...);       // 以新版本写入配置
        cache.evictAllCache(typeId);                          // 删除 Redis 缓存
    }
```

#### 方案 2：策略无状态约束（解决问题 2）

在 `ValidationStrategy` 接口 Javadoc 中明确约束：

```
集群部署约束：
1. 实现类必须无状态
2. 必须线程安全
3. 共享状态（如 API Token）必须存 Redis
```

如果策略需要缓存外部 API Token，使用 Redis 而非本地变量：

```java
// 正确：Token 存 Redis
String token = redisTemplate.opsForValue().get("license:verify:token");
if (token == null) {
    token = refreshApiToken();
    redisTemplate.opsForValue().set("license:verify:token", token, 1, TimeUnit.HOURS);
}
```

#### 方案 3：乐观锁 + 分布式锁兜底（解决问题 4）

**第一层：MyBatis-Plus 乐观锁（主方案）**

```java
// 跨实例安全，自动处理并发
@Version
private Integer version;
```

两个请求分到不同实例时，后一个请求会因为版本号不匹配而失败。

**第二层：Redis 分布式锁（可选兜底）**

```java
public RLock acquireStepLock(Long registerId, int stepOrder) {
    String lockKey = String.format("enterprise:step:%d:%d", registerId, stepOrder);
    RLock lock = redissonClient.getLock(lockKey);
    boolean acquired = lock.tryLock(3, 30, TimeUnit.SECONDS);
    if (!acquired) {
        throw new ValidationException("操作过于频繁，请稍后重试");
    }
    return lock;
}
```

#### 方案 4：异步回调幂等性（解决问题 5）


## 十三、面试高频问题预演

### Q1：为什么不用责任链？

**A**：三个原因：
1. **业务语义冲突**：责任链的自动传递机制与"分步提交"的业务需求冲突——经典责任链执行完第 1 步会自动调第 2 步，但我们需要"用户提交第 1 步 → 等待用户操作 → 再提交第 2 步"
2. **快照版本死锁**：如果用快照版本锁定配置结构，但管理员禁用了某个校验项（`status=DISABLED`），快照模式下的老用户会因为状态校验失败而无法继续流程
3. **查询性能**：责任链链表结构查找第 N 个节点需要 O(n)，而策略模式的 List 结构支持 O(1) 按序号索引

### Q2：策略模式和配置化引擎怎么配合？

**A**：策略模式负责"每个校验项的逻辑独立"，配置化引擎负责"步骤序列的装配和调度"。策略定义代码逻辑（Bean），配置表定义步骤顺序（数据），引擎根据配置动态加载策略列表。两者配合实现了"逻辑可插拔 + 流程可配置"。

### Q3：快照版本号怎么实现的？

**A**：通过独立的 `enterprise_config_version` 表原子管理。用户开始入驻时，`ConfigVersionService.currentVersion()` 从 Redis 缓存读取当前版本号（缓存未命中查库回填），写入入驻记录的 `config_version` 字段作为快照。管理员修改配置时，`nextVersion()` 使用 `INSERT ... ON DUPLICATE KEY UPDATE` 原子自增版本号，再以新版本写入 `validation_config`。新用户读新版本，老用户继续用旧版本，互不干扰。

### Q4：并发提交怎么控制？

**A**：用 MyBatis-Plus 乐观锁。在 `enterprise_register` 实体加 `@Version` 注解，每次更新时校验版本号是否一致。如果两个请求同时到达，后一个请求会因为版本号不匹配而失败，提示用户重试。比分布式锁（如 Redis SETNX）更轻量，适合低冲突场景。

### Q5：事务边界怎么处理的？

**A**：策略执行和结果保存分离。`executeStep()` 方法不开启事务——因为策略可能调用外部 API（如工商接口），耗时 5 秒以上。如果在事务中执行，数据库连接会被长时间占用。校验结果通过 `saveCheckResult()` 事务方法保存，只做 DB 操作，毫秒级完成。

### Q6：N+1 查询怎么优化的？

**A**：`loadStrategies()` 方法中，一次性查出所有 `validation_config` 记录（按 `type_id` + `config_version` 过滤），然后用 `getIdentifier()` 从 `strategyMap` 取对应的 Strategy Bean。避免了循环内逐条查库。

### Q7：回退后的数据一致性怎么保证？

**A**：回退时调用 `recordMapper.resetStepsAfter(registerId, targetStep)` 批量将目标步骤之后的所有校验记录置为 PENDING。同时用 `@Version` 乐观锁更新 `enterprise_register` 的 `currentStep`。保证了步骤状态的连续性。

### Q8：策略 Identifier 与 Bean Name 解耦有什么好处？

**A**：原来数据库存的是 Spring Bean Name（如 `businessLicenseStrategy`），代码重命名类会导致线上运行时才能报错。改进后用业务标识符（如 `BUSINESS_LICENSE`），通过 `StrategyIdentifier` 枚举统一管理，数据库存的是稳定的业务标识，代码重构完全不影响配置。

### Q9：如果需要异步校验（如人工审核）怎么办？

**A**：可以在 `ValidationStrategy` 接口增加异步版本：

```java
public interface AsyncValidationStrategy extends ValidationStrategy {
    /** 返回 true 表示需要异步等待结果 */
    boolean isAsync();
    /** 提交异步审核任务 */
    String submitAsync(ValidationContext ctx);
    /** 异步回调处理 */
    void onAsyncCallback(String taskId, Object result);
}
```

引擎检测到策略实现了 `AsyncValidationStrategy` 时，`executeStep()` 返回"审核中"状态，等回调时再更新结果。

### Q10：如何监控校验流程的性能和成功率？

**A**：在引擎的 `executeStep()` 方法中添加 Micrometer 指标埋点：

```java
Timer.Sample sample = Timer.start(metricsRegistry);
try {
    ValidationResult result = strategy.validate(ctx);
    sample.stop(timer);
    counter.increment();
    return result;
} catch (Exception e) {
    errorCounter.increment();
    sample.stop(errorTimer);
    throw e;
}
```

### Q11：集群部署时，各实例的配置缓存如何保持一致？

**A**：用 Redis 分布式缓存替代本地缓存。缓存 Key 是 `validation_config:{typeId}:{configVersion}`，所有实例共享同一份 Redis 数据。管理员修改配置后，调用 `cache.evictAllCache(typeId)` 删除 Redis Key，所有实例下次加载配置时会自动查库重建缓存，实现集群环境下的缓存一致性。

### Q12：集群下两个用户请求打到不同实例，会出问题吗？

**A**：不会。因为：
1. **配置一致性**：所有实例从 Redis 读取同一份校验配置，结果一致
2. **版本快照**：入驻时在 MySQL 锁定 configVersion，所有实例查出来的快照相同
3. **乐观锁**：MyBatis-Plus `@Version` 保证同一入驻记录不会被重复提交
4. **策略无状态**：策略 Bean 不持有任何实例状态，行为完全确定性

### Q13：集群下需要分布式锁吗？

**A**：默认不需要。MyBatis-Plus 的 `@Version` 乐观锁已经能处理大部分并发场景。只有在极端高并发（如秒杀级入驻）场景下，才会在乐观锁之前加一层 Redis 分布式锁做前置拦截。日常场景乐观锁足够。

### Q14：策略实现需要注意什么才能支持集群？

**A**：三个约束：
1. **无状态**：Bean 不能存任何实例级状态
2. **线程安全**：多线程并发调用同一个 Bean 方法不出问题
3. **共享状态存 Redis**：如果需要缓存 API Token 等共享数据，必须存 Redis 而非本地变量。例如 `String token = redisTemplate.opsForValue().get("token_key")`。

### Q15：集群下异步回调怎么处理？

**A**：异步回调到达时可能打到任一实例。处理逻辑是：
1. 通过 `taskId` 在 MySQL 查出入驻记录（快照版本在记录里，不受缓存影响）
2. 做幂等性检查：如果状态不是"等待回调"，直接返回
3. 调用引擎的 `saveAsyncResult()` 更新结果

如果担心重复回调，在方法上加 `@RedisLock(key = "'callback:' + #taskId")` 做分布式锁兜底。

### Q16：快照版本对应的配置被删除了怎么办？

**A**：快照存的是 `strategy_id`（业务标识符，如 `BUSINESS_LICENSE`），不是配置记录的 ID。只要对应 Bean 还在 Spring 容器中（`StrategyIdentifier` 枚举中仍有该标识符），就能正常构建链。即使 `validation_config` 表的旧版本记录被清理，也不会影响已有快照的解析。

### Q17：Redis 缓存序列化方案为什么选 StringRedisTemplate + Jackson？

**A**：三个原因：
1. **可读性好**：JSON 格式的数据可以直接用 `redis-cli` 查看和排查，而默认序列化后的二进制数据无法阅读
2. **支持复杂类型**：`GenericJackson2JsonRedisSerializer` 支持 `LocalDateTime`、`BigDecimal`、继承关系等复杂对象的序列化
3. **跨语言兼容**：JSON 是通用格式，如果未来其他服务（如 Python 脚本）需要读缓存，可以直接解析 JSON

### Q18：Redis 缓存穿透怎么防的？

**A**：对于查不到配置的请求（如不存在的 `configVersion`），缓存一个空值标记 `EMPTY`，TTL 为 1 分钟。1 分钟内相同请求直接返回空列表，不会穿透到数据库。配合版本号的合法性校验，可以有效防止恶意攻击或 Bug 导致的缓存穿透。

### Q19：config_version 用独立表管理有什么好处？

**A**：三个好处：
1. **原子性**：`INSERT ... ON DUPLICATE KEY UPDATE` 保证高并发下版本号不会跳变（原来的 `UPDATE ... SET version = version + 1` 在某些隔离级别下可能丢失更新）
2. **读写分离**：版本号生成（写操作，配置变更时触发）和读取（读操作，入驻时触发）解耦，读操作走 Redis 缓存，性能极高
3. **可扩展**：未来如果需要更复杂的版本控制（如版本回滚、版本审计），独立表更易扩展
