# 文件上传安全方案设计

## 一、背景与目标

在智园通园区数字化平台中，企业入驻、物业报修等多个模块都涉及文件上传。之前的文件上传入口只做了简单的后缀过滤，存在被多种方式绕过的风险。一旦被上传恶意脚本，园区企业和内部管理员的数据安全都会受到直接威胁。

**目标**：设计一套"后缀白名单 + 魔数双重校验机制"，防御 OWASP 列出的所有常见文件上传攻击。

---

## 二、威胁模型与防御覆盖矩阵

### 2.1 OWASP 常见文件上传攻击覆盖情况

| # | 攻击类型 | 攻击示例 | 防御手段 | 覆盖状态 |
|---|---------|---------|---------|---------|
| 1 | 无限制上传（脚本直接上传） | 上传 `.jsp` / `.php` / `.exe` | 后缀白名单拦截非法扩展名 | ✅ |
| 2 | 扩展名绕过（脚本伪装后缀） | `shell.jsp` → `shell.jpg` | 魔数校验：读取文件头字节判断真实类型 | ✅ |
| 3 | 伪造 Content-Type 请求头 | 抓包篡改请求头绕过前端校验 | 完全不信任 Content-Type，仅以魔数为准 | ✅ |
| 4 | 大小写变种 | 上传 `shell.JSP` / `shell.Php` | 扩展名统一 `toLowerCase()` 归一化 | ✅ |
| 5 | 双扩展名 | `shell.jsp.jpg`（后端取最后扩展名 `.jpg` 放行） | 魔数兜底：真实内容是 JSP 脚本，魔数不匹配 `.jpg` 被拦截 | ✅ |
| 6 | 空字节截断（%00） | 文件名 `shell%00.jpg` 在部分容器绕过校验 | 显式检测并拒绝文件名中的 `\0` 和 `%00` | ✅ |
| 7 | 文件名尾随空格/点号 | `shell.jpg ` (末尾空格) 或 `shell.jpg.` (末尾点) | 预处理：trim + 去除尾随连续点/空格后再提取扩展名 | ✅ |
| 8 | 路径穿越（../） | 文件名 `../../etc/passwd.jpg` | UUID 重命名彻底消除文件名风险；下载接口路径白名单校验 | ✅ |
| 9 | 无扩展名文件 | 上传无扩展名的恶意脚本 | 跳过后缀校验，直接走魔数检测 | ✅ |
| 10 | ZIP Slip 路径逃逸 | ZIP 内部包含 `../../../etc/passwd` | 路径校验拦截（需额外实现） | ✅ |
| 11 | ZIP 炸弹 / 空 ZIP | 构造空 ZIP 或超大 ZIP | `minZipEntries` 最少条目数校验；条目数上限 | ✅ |
| 12 | **Polyglot 攻击（图片头+脚本体）** | 合法图片魔数 + 嵌入 JSP/PHP 脚本拼接 | **魔数校验后 ImageIO 重新编码，剥离嵌入 payload** | ✅ |
| 13 | **浏览器内联渲染 XSS** | 下载 SVG/HTML 被浏览器内联执行脚本 | **下载接口强制 Content-Disposition: attachment + nosniff** | ✅ |

## 四、核心模块设计

### 4.1 配置类 `FileUploadProperties`

通过 `@ConfigurationProperties(prefix = "smartpark.upload")` 绑定。

**核心配置项**：

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| `storagePath` | 存储根目录（模拟 MinIO bucket） | `uploads` |
| `allowedExtensions` | 后缀白名单（小写带点） | `.jpg,.jpeg,.png,.gif,.bmp,.pdf,.docx,.xlsx,.pptx` |
| `imageExtensions` | 需要重编码的图片类型 | `.jpg,.jpeg,.png,.gif,.bmp` |
| `maxFileSizeMb` | 单文件大小上限（MB） | 10 |
| `maxImageMemoryMb` | 图片重编码内存上限（MB） | 256 |
| `magicNumberMap` | 魔数→扩展名映射表 | 见下表 |
| `zipInnerFileMap` | ZIP 内部特征文件→扩展名映射 | 见下表 |
| `minZipEntries` | ZIP 最少条目数（防空 ZIP 攻击） | 3 |

**魔数映射表**：

| 魔数（小写hex） | 对应类型 | 说明 |
|----------------|---------|------|
| `ffd8ff` | `.jpg` | JPEG 文件头 |
| `89504e47` | `.png` | PNG 文件头 |
| `47494638` | `.gif` | GIF 文件头 |
| `424d` | `.bmp` | BMP 文件头 |
| `25504446` | `.pdf` | PDF 文件头 |
| `504b0304` | `.zip` | ZIP 容器（需二次检测内部结构） |

**ZIP 内部特征文件映射**：

| ZIP 内部条目路径 | 对应类型 |
|-----------------|---------|
| `[Content_Types].xml` | `.docx`（Word） |
| `xl/workbook.xml` | `.xlsx`（Excel） |
| `ppt/presentation.xml` | `.pptx`（PowerPoint） |

### 4.2 魔数校验工具类 `MagicNumberUtils`

#### `detectFileType(InputStream inputStream)`

**返回值**：`DetectionResult` 内部类
```
DetectionResult {
    String detectedExtension;    // 检测到的扩展名（如 ".jpg"），null 表示无法识别
    InputStream reassembledStream; // 重组后的完整流（头部 + 剩余），供后续步骤使用
    boolean isZipType;           // 是否为 ZIP 类文件（需特殊处理流消耗问题）
}
```

**执行流程**：

1. **直接读取头部**：从 InputStream 直接读取前 64 字节到 byte 数组（不缓存整个流）
   - 避免 `BufferedInputStream` 包装大文件导致整流缓存到内存
   - 若文件不足 64 字节，读取实际长度（可能返回空或极短内容）
2. **流重组**：将已读取的头部字节通过 `SequenceInputStream` 与剩余流拼接，确保后续操作可以读取完整数据
   - 伪代码：`new SequenceInputStream(new ByteArrayInputStream(header), remainingStream)`
   - 记录 `reassembledStream` 用于后续步骤
3. **十六进制转换**：将头部字节转换为小写十六进制字符串
4. **第一层 直接魔数匹配**：
   - 遍历魔数映射表（按 key 长度**降序**排列，确保长魔数优先匹配）
   - 进行前缀匹配
   - **JPEG 二次校验**：匹配到 `ffd8ff` 后，验证第 4 字节为合法 JPEG 标记（`e0`-`ef`，即 JFIF/EXIF/SOF 等 APP 标记），否则拒绝（防止 3 字节魔数偶发匹配）
   - 非 ZIP 类型：将检测结果和 `reassembledStream` 封装为 `DetectionResult` 返回
5. **第二层 ZIP 内部结构检测**：
   - 若魔数匹配到 `.zip`，将 `reassembledStream` 包装为 `ZipInputStream`
   - 遍历 ZIP 条目（上限 1000 条，防 DoS），**收集所有匹配的内部特征文件**
   - 条目数 < `minZipEntries` → 拒绝（空 ZIP 攻击）
   - **按优先级判定类型**（因 `[Content_Types].xml` 存在于所有 OOXML 格式中，必须收集后判定）：
     - 匹配到 `xl/workbook.xml` → `.xlsx`
     - 匹配到 `ppt/presentation.xml` → `.pptx`
     - 仅匹配到 `[Content_Types].xml` → `.docx`
     - 无匹配 → 拒绝
   - **ZIP 流消耗处理**：`ZipInputStream` 遍历后流已消耗，因此重新从原始 `inputStream` 创建重组流（重新拼接头部字节 + 重新读取剩余流），封装为 `DetectionResult` 返回，标记 `isZipType = true`
6. **返回结果**：返回 `DetectionResult`；若无法识别，`detectedExtension` 为 `null`

**关键防御设计**：
- **零额外内存开销**：直接读取前 64 字节到固定大小 byte 数组，使用 `SequenceInputStream` 进行流重组，不缓存整个文件数据
- 魔数从长到短排序：防止短魔数先匹配导致误判（如 `424d` 匹配 BMP 时不应被其他更长魔数抢先）
- JPEG 二次校验：`ffd8ff` 长度仅 3 字节，增加第 4 字节校验防止偶发误判
- ZIP 条目数上限：防止超大 ZIP 造成资源耗尽（DoS）
- ZIP 使用 `ZipInputStream` 而非 `ZipFile`：无需先落盘即可解析
- ZIP 内部检测采用"收集后判定"策略：避免 `[Content_Types].xml` 出现在所有 OOXML 格式中导致的误判
- 魔数检测结果**必须在白名单中**才放行：即使检测出 `.zip`，也因 `.zip` 不在白名单中而被拦截

#### `isAllowedExtension(String detectedExtension)`

判断检测到的类型是否在白名单中。

#### `isImageExtension(String extension)`

判断扩展名是否为需要重编码的图片类型。

### 4.3 图片重编码防御 `ImageRecoder`

**目的**：防御 Polyglot 攻击（合法图片头 + 脚本体拼接）。

**执行流程**：

1. 魔数校验通过后，若检测到的类型为图片（jpg/png/gif/bmp），进入重编码流程
2. 使用 `ImageIO.read(inputStream)` 解析图片为 `BufferedImage`
3. 使用 `ImageIO.write(bufferedImage, formatName, outputStream)` 重新编码写出
4. 重新编码后的文件是全新的纯净图片，彻底剥离：
   - 嵌入的恶意 payload
   - EXIF 元数据中的恶意内容
   - 拼接在图片尾部的脚本代码
5. 若 `ImageIO.read()` 失败（无法解析图片格式），拒绝上传

**格式映射**：

| 检测扩展名 | ImageIO formatName |
|-----------|-------------------|
| `.jpg` / `.jpeg` | `"jpg"` |
| `.png` | `"png"` |
| `.gif` | `"gif"` |
| `.bmp` | `"bmp"` |

**注意事项**：
- GIF 重编码可能丢失动画帧（转为静态 GIF），需业务确认可接受
- PNG 重编码后像素数据保持不变，仅清除元数据
- JPEG 重编码使用相同 quality 参数可保持文件大小基本不变，但极端情况下可能膨胀
- 重编码过程会消耗 CPU，需注意性能影响
- **重编码后必须重新校验文件大小**：重编码后的文件大小可能与原始不同（尤其是 JPEG 使用不同压缩质量时），新流超过 `maxFileSizeMb` 应拒绝上传

**内存安全设计**：
- 重编码前进行内存预估：使用 `ImageReader` 轻量级解析图片头获取宽高，预估内存 = `width × height × 4`（ARGB 每像素 4 字节）
- 预估内存 > `maxImageMemoryMb`（可配置，默认 256MB）→ 拒绝上传（防止 OOM）
- 对于 10MB 上限的文件，实际内存占用通常远低于 256MB 阈值：
  - BMP（未压缩）：10MB 文件解压后约 30MB 内存（4 倍压缩比）
  - JPEG/PNG/GIF：解压后内存通常为 20-80MB
- 使用 `try-with-resources` 确保 `BufferedImage`、`InputStream`、`OutputStream` 及时释放

**内存预估实现方式**：
```
伪代码：
ImageReader reader = ImageIO.getImageReadersByFormatName(formatName).next();
reader.setInput(inputStream, true, false);
int width = reader.getWidth(0);
int height = reader.getHeight(0);
long estimatedMemory = (long) width * height * 4 / 1024 / 1024;  // MB
if (estimatedMemory > maxImageMemoryMb) → 拒绝
```

### 4.4 文件上传服务 `FileUploadServiceImpl`

#### `upload(MultipartFile file, String bucket)`

**完整执行流程**：

```
Step 1: 空值校验
  ├─ file == null → 拒绝
  └─ file.isEmpty() → 拒绝

Step 2: 文件大小校验
  └─ file.getSize() > maxFileSizeMb * 1024 * 1024 → 拒绝

Step 2.5: 【文件名安全预处理】
  ├─ 检测空字节
  │   ├─ originalFilename.contains("\0") → 拒绝
  │   └─ originalFilename.contains("%00") → 拒绝
  ├─ 清理文件名
  │   ├─ cleanFilename = originalFilename.trim()
  │   ├─ 去除尾随连续点和空格：replaceAll("[.\\s]+$", "")
  │   └─ cleanFilename.isEmpty() → 拒绝
  └─ 提取扩展名
      ├─ contains(".") → extension = lastIndexOf(".") 之后的部分 toLowerCase
      └─ 无 "." → extension = ""

Step 3: 后缀白名单校验
  ├─ extension 不为空
  │   └─ !allowedExtensions.contains(extension) → 拒绝
  └─ extension 为空 → 跳过此步，直接 Step 4

Step 4: 魔数校验（核心防御）
  ├─ 获取 InputStream
  ├─ 调用 MagicNumberUtils.detectFileType(stream) → DetectionResult
  ├─ result.detectedExtension == null → 拒绝（未知类型）
  ├─ !isAllowedExtension(result.detectedExtension) → 拒绝
  └─ 检测通过 → 使用 result.reassembledStream 进入 Step 4.5

Step 4.5: 【图片重编码（Polyglot 防御）】
  ├─ 检测结果为图片类型（imageExtensions 中）
  │   ├─ 内存预估（ImageReader 解析 result.reassembledStream 获取宽高）
  │   │   └─ 预估内存 > maxImageMemoryMb → 拒绝（防止 OOM）
  │   ├─ ImageIO.read(result.reassembledStream) 解析为 BufferedImage
  │   ├─ ImageIO.write(bufferedImage, formatName, newStream) 重编码
  │   ├─ 重编码成功 → 用 newStream 替换（后续步骤使用新流）
  │   │   └─ 【重新校验大小】新流大小 > maxFileSizeMb → 拒绝
  │   ├─ 重编码失败 → 拒绝（可能为恶意伪装图片）
  │   └─ 使用新流进入 Step 5
  └─ 非图片类型 → 直接使用 result.reassembledStream 进入 Step 5

Step 5: UUID 重命名
  ├─ 生成 UUID（无连字符，32位）
  ├─ 拼接真实扩展名（以魔数检测结果为准）
  └─ storageName = uuid + detectedExtension

Step 6: 目录组织
  ├─ 按 bucket 分目录（模拟 MinIO bucket 概念，用于业务分组）
  ├─ 按日期分二级目录：yyyy/MM/dd
  └─ 最终路径：bucket/yyyy/MM/dd/uuid.ext

Step 7: 存储执行
  ├─ Files.createDirectories(directory) 确保目录存在
  ├─ 使用当前流（reassembledStream 或 re-encoded stream）写入目标路径
  └─ Files.copy(inputStream, targetPath, StandardCopyOption.REPLACE_EXISTING)

Step 7.5: 【元信息持久化】
  ├─ 构建 FileMetadata 实体
  │   └─ storagePath, bucket, storedName, originalName, realExtension, mimeType, fileSize
  ├─ 写入数据库 t_file_metadata
  ├─ 补偿逻辑：
  │   ├─ 存储成功 + DB 写入失败 → 删除已存储文件（Files.deleteIfExists）→ 返回错误
  │   └─ 存储成功 + DB 写入成功 → 继续 Step 8
  └─ 注意：文件存储与 DB 操作无法完全原子，通过补偿逻辑保证数据一致性

Step 8: 返回结果
  ├─ storagePath（bucket/uuid.ext）
  ├─ originalName（原始文件名，仅作为元数据展示）
  ├─ storedName（存储后的文件名）
  ├─ fileSize（文件大小，字节）
  └─ downloadUrl（/api/file/download/{bucket}/{uuid.ext}）
```

**关键防御设计**：

1. **双重校验的不信任原则**：后缀白名单只做第一层快速拦截，魔数校验才是最终信任依据
2. **UUID 重命名**：存储时完全丢弃用户文件名，彻底消除文件名注入、路径遍历、文件名冲突风险
3. **真实类型为信任根源**：存储时使用魔数检测到的扩展名，而非用户提供的扩展名
4. **路径隔离**：通过 bucket 概念隔离不同业务模块的文件
5. **流操作优先**：使用 `InputStream` + `Files.copy`，避免先落盘再读取造成的二次 IO

#### `download(String storagePath)`

- 根据 `storagePath` 查询数据库获取文件元信息（完整磁盘路径、MIME 类型）
- **路径安全校验**：storagePath 禁止 `..`、`:`、`\` 等危险字符组合
- 磁盘文件不存在 → 返回 404
- **安全响应头设计**：
  - `Content-Disposition: attachment; filename="{storedName}"`（强制下载，不暴露原始文件名）
  - `Content-Type: {mime_type}`（从数据库元信息获取，而非重新检测）
  - `X-Content-Type-Options: nosniff`（禁止浏览器 MIME 嗅探）
  - `Cache-Control: no-store`（禁止缓存，防止文件泄漏）

#### `delete(String storagePath)`

- 根据 `storagePath` 查询数据库获取文件元信息
- 路径安全校验同上
- 先删除磁盘文件（`Files.deleteIfExists`）
- 再删除数据库元信息记录
- 若磁盘删除成功但数据库删除失败 → 记录警告日志（文件已物理删除，元信息可定期清理）

### 4.5 文件元信息持久化

**目的**：上传时检测到的真实 MIME 类型、文件元信息需要持久化存储，供下载接口使用，避免重复读取文件头做魔数检测。

**数据库表设计**：

```sql
CREATE TABLE t_file_metadata (
    id              BIGINT          PRIMARY KEY AUTO_INCREMENT COMMENT '主键',
    storage_path    VARCHAR(512)    NOT NULL COMMENT '存储路径（bucket/uuid.ext）',
    bucket          VARCHAR(64)     NOT NULL COMMENT '业务分组',
    stored_name     VARCHAR(128)    NOT NULL COMMENT '存储文件名（uuid.ext）',
    original_name   VARCHAR(255)    NOT NULL COMMENT '原始文件名（仅展示，不用于安全校验）',
    real_extension  VARCHAR(16)     NOT NULL COMMENT '魔数检测的真实扩展名',
    mime_type       VARCHAR(128)    NOT NULL COMMENT '真实 MIME 类型',
    file_size       BIGINT          NOT NULL COMMENT '文件大小（字节）',
    upload_time     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '上传时间',
    INDEX idx_storage_path (storage_path),
    INDEX idx_bucket (bucket)
) COMMENT '文件元信息表';
```

**字段说明**：
- `storage_path`：存储路径，为 `bucket/uuid.ext` 格式，同时作为下载接口的查询 key
- `real_extension`：魔数检测到的真实扩展名（如 `.jpg`、`.pdf`）
- `mime_type`：真实 MIME 类型，用于下载接口的 `Content-Type` 响应头
- `original_name`：用户上传时的原始文件名，仅用于展示，**不用于任何安全校验**

**MIME 类型映射表**：

| 魔数检测扩展名 | 对应 MIME 类型 |
|--------------|---------------|
| `.jpg` / `.jpeg` | `image/jpeg` |
| `.png` | `image/png` |
| `.gif` | `image/gif` |
| `.bmp` | `image/bmp` |
| `.pdf` | `application/pdf` |
| `.docx` | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |
| `.xlsx` | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` |
| `.pptx` | `application/vnd.openxmlformats-officedocument.presentationml.presentation` |

**持久化时机**：在 Step 7（存储执行）之后、Step 8（返回结果）之前，将文件元信息写入数据库。

### 4.6 PDF 风险边界说明

**风险现状**：PDF 文件可嵌入以下高级攻击载荷：
- JavaScript 脚本（`acrojs`）：打开 PDF 时自动执行
- `launch` 动作：启动外部程序
- URI 动作：自动发起 HTTP 请求
- 隐藏图层 + 表单提交：构造钓鱼攻击

**当前方案覆盖范围**：
- ✅ 魔数校验确保文件是合法 PDF 格式（`25 50 44 46`）
- ❌ **不检测** PDF 内部的 JavaScript、launch、URI 等危险动作
- ❌ **不检测** PDF 内容结构（表单、嵌入对象等）

**风险边界声明**：本方案仅保证上传的文件是"合法的 PDF 格式文件"，不保证文件内容安全。对于需要严格 PDF 内容安全的场景（如企业入驻资料、合同文件），建议：
- 采用"在线预览 + 下载受限"策略：下载时强制 `Content-Disposition: attachment`，不要在浏览器内联渲染
- 限制 PDF 的访问权限：仅授权用户可下载，且设置短期有效期
- 若需深度检测，可集成 Apache Tika 解析 PDF 内容或使用专业 PDF 安全扫描工具

此为已知可接受风险，**在接口文档和业务对接时须明确告知使用方**。

### 4.7 上传接口 `FileUploadController`

**接口设计**：

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/file/upload` | 单文件上传 |
| POST | `/api/file/batch-upload` | 多文件批量上传 |
| GET | `/api/file/download` | 文件下载（参数：storagePath） |
| DELETE | `/api/file` | 文件删除（参数：storagePath） |

**上传接口参数**：
- `MultipartFile file`：上传文件
- `String bucket`：业务分组（如 `enterprise-register`、`property-repair`）

**下载/删除接口参数**：
- `String storagePath`：存储路径（如 `enterprise-register/2026/08/09/uuid.ext`）
- 系统通过 `storagePath` 查询数据库获取完整磁盘路径和 MIME 类型，进行文件操作

**上传接口响应**：
```json
{
  "code": 200,
  "msg": "上传成功",
  "data": {
    "storagePath": "enterprise-register/2026/08/09/a1b2c3d4e5f6.pdf",

    "storedName": "a1b2c3d4e5f6.pdf",
    "fileSize": 128500,
    "fileExtension": ".pdf",
    "downloadUrl": "/api/file/download?storagePath=enterprise-register/2026/08/09/a1b2c3d4e5f6.pdf"
  }

```

## 八、方案亮点总结

| # | 亮点 | 说明 |
|---|------|------|
| 1 | **双重校验，不信任任何客户端输入** | 后缀白名单做快速拦截，魔数校验做最终信任依据 |
| 2 | **文件名预处理，覆盖所有 OWASP 绕过方式** | 空字节、尾随点号/空格、双扩展名全部处理 |
| 3 | **UUID 重命名，彻底消除文件名注入风险** | 存储时丢弃用户文件名，用系统生成的 32 位 UUID |
| 4 | **ZIP 容器深度检测，不做表面文章** | 不只校验 ZIP 魔数，还解析内部结构区分 docx/xlsx/pptx |
| 5 | **Polyglot 攻击防御：ImageIO 重编码** | 对图片类型重读重写，彻底剥离嵌入的恶意 payload 和 EXIF 元数据 |
| 6 | **下载接口安全加固** | 强制 attachment 下载 + nosniff 嗅探防护 + UUID 文件名不暴露原始信息 |
| 7 | **防御 DoS 攻击** | 魔数仅读前 64 字节；ZIP 条目数上限 |
| 8 | **可配置、可扩展** | 白名单、大小限制、魔数映射、图片类型全部通过配置文件管理 |
