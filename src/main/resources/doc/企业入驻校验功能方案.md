# 企业入驻校验功能方案

---

## 一、需求描述

**业务背景**

smartPark 智慧园区管理系统面向多类企业提供入驻服务。不同企业类型在入驻前需要经过不同的前置校验流程，且校验以分步页面呈现，当前校验项通过后才能进入下一项。

**核心需求**

1. **多类型差异化校验** — 不同企业类型有不同的校验步骤链。例如：
   - 科技研发类：营业执照有效性 → 法人信息
   - 金融类：营业执照有效性 → 法人信息 → 金融许可证

2. **严格线性流转** — 第 N 步校验未通过，不能进入第 N+1 步，不可跳过。

3. **分步页面交互** — 每个校验项独立页面，用户填写完成后手动点击"提交校验"，而非一次性全部提交。

4. **回退修改** — 用户可回退到之前已通过的步骤修改信息，修改后后续步骤状态需自动重置，需要重新校验。

5. **草稿保存** — 用户可随时退出入驻流程，再次进入时恢复之前已填写的进度，无需重新开始。

6. **管理员终审** — 所有校验项通过后，生成入驻申请，需管理员最终审核通过才完成入驻。

7. **配置化可扩展** — 未来新增企业类型或校验项时，只需修改数据库配置，无需改动业务代码。

---

## 二、解决思路

### 2.1 核心矛盾分析

该需求的核心矛盾在于：

```
"校验项之间有严格的顺序关系"  vs  "每种企业类型的校验项数量和内容不同"
```

这意味着解决方案需要同时满足：
- **顺序控制** — 能表达"A必须在B之前执行"的链式关系
- **配置化** — 链的组成（节点数量和顺序）由外部配置驱动，而非硬编码

### 2.2 本质抽象

将业务抽象为三层模型：

```
第一层：企业类型层      → 定义有哪些企业类型（科技研发类、金融类……）
第二层：步骤链配置层    → 定义某类型企业依次经过哪些校验步骤（第1步做什么、第2步做什么……）
第三层：校验执行层      → 每个步骤的具体校验逻辑怎么执行
```

三层之间完全解耦：
- 新增企业类型 → 只需操作第一层 + 第二层（配置）
- 新增校验项 → 只需操作第三层 + 第二层（实现 + 配置）
- 调整顺序 → 只需操作第二层（配置）

### 2.3 核心设计方向

需要一个**可配置的校验步骤链 + 能控制链的推进和回退的引擎**：

```
数据库配置（企业类型 → 步骤列表）
        │
        ▼
  链构造器（按顺序组装步骤节点）
        │
        ▼
  步骤引擎（控制：当前在哪一步 → 执行校验 → 推进/回退）
```

## 三、解决方案

### 3.1 可选方案

#### 方案 A：策略模式 + 步骤引擎

**核心思想**：每个校验项是一个独立的策略（Strategy），由步骤引擎根据当前步骤序号路由到对应的策略执行。

```
StepEngine.execute(registerId)
    → currentStep = 2
    → 从 Map<stepOrder, Strategy> 中找到 strategy_2
    → strategy_2.execute(data)
    → 返回结果
```

**优点**：
- 实现简单，每个策略互相独立
- 易于测试（每个策略可单独测试）
- 接口清晰：`Strategy.execute(数据) → 结果`

**缺点**：
- 业务语义不够直观 — "一条依次执行的校验链"在代码中表达为"从Map中取策略"，语义丢失
- 后续维护者看到代码，无法直观理解"这是一条链"

#### 方案 B：经典责任链模式（链表结构）

**核心思想**：每个校验项是一个 Handler，持有下一个 Handler 的引用，形成一个单向链表。

```java
public abstract class CheckHandler {
    protected CheckHandler next;
    public void setNext(CheckHandler next) { this.next = next; }
    public CheckResult handle(Request request) {
        // 执行当前节点逻辑
        if (passed && next != null) {
            return next.handle(request);  // 自动传递到下一个
        }
        return result;
    }
}
```

**优点**：
- 业务语义精准匹配 — "校验链"的概念和代码结构完全一致
- 经典设计模式，团队认知成本低

**缺点**：
- **无法适配分步交互** — 经典责任链是"自动传递"的，执行完一个节点自动调用下一个。但我们的场景需要"执行完第1步 → 等待用户确认 → 再执行第2步"，自动传递在这里反而成了问题
- 链接关系在代码中硬编码（`next` 引用），不利于配置化

#### 方案 C：配置化责任链模式（List 结构 + 步骤引擎）← 最终选择

**核心思想**：用责任链的语义组织业务逻辑，用数据库配置驱动链的构建，用步骤引擎控制链的执行进度。

```java
// 链 = 有序的节点列表，由 DB 配置动态构建
List<CheckHandler> chain = chainBuilder.build(enterpriseType);

// 引擎控制执行，不自动传递
StepEngine.execute(registerId)
    → currentStep = 2
    → chain.get(2).check(data)     // 只执行当前节点
    → 等待用户下一次触发
```

### 3.2 方案对比

| 对比维度 | 策略模式+引擎 | 经典责任链 | 配置化责任链（选择） |
|---------|:-----------:|:---------:|:----------------:|
| **业务语义匹配度** | ★★★☆☆ — 策略是并列关系，与"链式校验"语义不符 | ★★★★★ — 链式结构与业务完全吻合 | ★★★★★ — 保留责任链的"链"语义 |
| **分步交互支持** | ★★★★★ — 引擎天然支持按步骤调度 | ★★☆☆☆ — 自动传递与本场景矛盾 | ★★★★★ — 引擎控制，不自动传递 |
| **配置化扩展** | ★★★★★ — 配置驱动，新增策略无需改代码 | ★★☆☆☆ — 链接关系需代码维护 | ★★★★★ — DB配置驱动，零代码扩展 |
| **回退重置能力** | ★★★★★ — 按索引重置，简单直接 | ★★☆☆☆ — 需遍历链表重置节点 | ★★★★★ — 按索引重置，简单直接 |
| **代码复杂度** | ★★★★★ — 简单直观 | ★★★☆☆ — 需维护next引用 | ★★★★☆ — 略高于策略模式 |
| **可测试性** | ★★★★★ — 每个策略独立测试 | ★★★★☆ — 需处理链接关系 | ★★★★★ — 节点独立，引擎可mock |
| **团队理解成本** | ★★★★☆ — 策略模式普遍熟悉 | ★★★★★ — 经典模式，认知成本低 | ★★★★☆ — 略有变体，需简单说明 |

**加权总评**：

| 维度 | 权重 | 策略+引擎 | 经典责任链 | 配置化责任链 |
|-----|:---:|:---------:|:---------:|:----------:|
| 业务语义 | 25% | 3 | 5 | 5 |
| 分步交互 | 20% | 5 | 2 | 5 |
| 配置化 | 20% | 5 | 2 | 5 |
| 回退 | 10% | 5 | 2 | 5 |
| 复杂度 | 10% | 5 | 3 | 4 |
| 可测试 | 10% | 5 | 4 | 5 |
| 认知成本 | 5% | 4 | 5 | 4 |
| **加权总分** | 100% | **4.35** | **3.15** | **4.85** |

### 3.3 最终选择与原因

**选择方案 C：配置化责任链模式**

原因有三：

1. **业务语义准确** — "一串校验项依次执行"就是责任链的经典场景，用策略模式来表达会让后续维护者困惑：为什么一条校验链叫策略？命名与业务对不上，增加理解成本。

2. **避免经典责任链的"过度设计"** — 经典责任链用 `next` 引用形成链表，是为了实现"自动传递"。本场景不需要自动传递（需要等待用户触发），用 List 组织节点完全够用，还能天然支持按索引回退。

3. **配置化是最关键的差异点** — 经典责任链的链接关系通常硬编码在代码中，无法灵活调整。而用数据库配置步骤顺序，是企业类型多样化的业务场景的刚性需求。

### 4.2 数据库设计

#### 表结构

| 表名 | 说明 | 关键字段 |
|------|------|---------|
| `enterprise_type` | 企业类型配置，定义园区有哪些企业类型 | id, name, code, status |
| `check_item_def` | 校验项定义，定义所有可用的校验项及其处理器 | id, name, code, handler_bean, status |
| `enterprise_type_check` | ★ 核心配置表，定义某类型企业依次经过哪些校验步骤 | id, type_id, check_item_id, step_order, status |
| `enterprise_register` | 企业入驻申请表，记录入驻信息、当前步骤和进度状态 | id, 企业信息字段, current_step, status, draft_data |
| `enterprise_check_record` | 校验记录表，记录每步校验的执行结果 | id, register_id, check_item_id, step_order, check_status, check_result |

#### 配置化示例

在 `enterprise_type_check` 表中配置：

```
type_id=科技研发类, check_item_id=营业执照, step_order=1
type_id=科技研发类, check_item_id=法人信息,   step_order=2

type_id=金融类, check_item_id=营业执照,     step_order=1
type_id=金融类, check_item_id=法人信息,       step_order=2
type_id=金融类, check_item_id=金融许可证,     step_order=3
```

新增企业类型只需在该表中插入新记录，无需改动任何代码。

### 4.3 枚举定义

| 枚举 | 说明 | 值 |
|------|------|-----|
| `RegisterStatus` | 入驻状态 | DRAFT→CHECKING→ALL_CHECKED→PENDING_REVIEW→APPROVED/REJECTED |
| `CheckStatus` | 校验状态 | PENDING / PASSED / FAILED |

### 4.4 责任链节点 — CheckHandler 接口

```java
public interface CheckHandler {
    /**
     * 执行校验
     * @param request  校验请求（含入驻申请信息和当前步骤数据）
     * @return 校验结果（通过/失败 + 详情）
     */
    CheckResult check(CheckRequest request);
}
```

每个校验项实现一个 Handler，通过 `@Component` 注册为 Spring Bean，Bean 名称与 `check_item_def.handler_bean` 字段对应。

#### 内置 Handler 实现

| Handler | Bean名称 | 说明 |
|---------|---------|------|
| `BusinessLicenseHandler` | businessLicenseHandler | 校验营业执照有效性（调用工商接口或文档审核） |
| `LegalPersonHandler` | legalPersonHandler | 校验法定代表人信息真实性 |
| `FinancialLicenseHandler` | financialLicenseHandler | 校验金融许可证有效性 |

新增校验项只需：① 实现 Handler 接口 ② 在 `check_item_def` + `enterprise_type_check` 表中配置。

### 4.5 校验链 — CheckChain

```java
public class CheckChain {
    private final List<CheckHandler> nodes;       // 有序的责任链节点
    private final List<StepInfo> stepInfos;        // 步骤元信息（名称、编码等）

    public CheckHandler getNode(int stepOrder) {
        return nodes.get(stepOrder - 1);  // stepOrder 从1开始
    }

    public int getTotalSteps() {
        return nodes.size();
    }

    public List<StepInfo> getStepInfos() { ... }
}
```

```java

}
```

### 4.7 步骤引擎 — StepEngine

核心业务逻辑，负责校验流程的调度控制。

```java
@Component
public class StepEngine {

    /**
     * 执行当前步骤的校验
     * 1. 校验前置步骤是否已通过
     * 2. 从链中获取当前节点
     * 3. 执行 handler.check()
     * 4. 保存校验记录
     * 5. 若通过，推进到下一步；若失败，返回失败原因
     */
    public CheckResult executeStep(EnterpriseRegister register, CheckChain chain) { ... }

    /**
     * 推进到下一步
     * 更新 register.current_step + 1
     */
    public void moveToNext(EnterpriseRegister register) { ... }

    /**
     * 回退到指定步骤
     * 1. 更新 register.current_step
     * 2. 重置该步骤之后的所有校验记录为 PENDING
     */
    public void rollback(EnterpriseRegister register, int targetStep) { ... }

    /**
     * 校验上一步是否已通过
     */
    public void validatePreviousStepPassed(Long registerId, int currentStep) { ... }
}
```

### 4.9 接口设计

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/enterprise/types` | 获取所有启用的企业类型列表 |
| `POST` | `/enterprise/register/start` | 开始入驻，选择企业类型，生成草稿申请 |
| `GET` | `/enterprise/register/{id}/progress` | 获取入驻进度（当前步骤、总步骤数、各步骤状态） |
| `GET` | `/enterprise/register/{id}/steps` | 获取该入驻申请的所有校验步骤元信息 |
| `POST` | `/enterprise/register/{id}/step/{stepOrder}/save` | 保存当前步骤的草稿数据 |
| `GET` | `/enterprise/register/{id}/step/{stepOrder}` | 获取某步骤已保存的草稿数据 |
| `POST` | `/enterprise/register/{id}/step/{stepOrder}/submit` | 提交当前步骤进行校验 |
| `POST` | `/enterprise/register/{id}/step/back` | 回退到上一步 |
| `POST` | `/enterprise/register/{id}/submit` | 所有校验通过后，提交入驻申请进入待审核 |

### 4.12 方案亮点

1. **命名即业务** — 代码中直接使用 `CheckHandler`（责任链节点）、`CheckChain`（校验链），接手的人一看就理解业务逻辑是一串依次执行的校验。

2. **配置化零代码扩展** — 新增企业类型只需要在 `enterprise_type_check` 表中配置步骤链，新增校验项只需要实现一个 Handler + 一条 DB 记录，完全符合开闭原则。

3. **引擎与链分离** — 链负责"有哪些节点"（结构），引擎负责"执行到哪个节点"（状态），各司其职，互不耦合。

4. **分步交互友好** — 引擎不自动传递节点，每次只执行当前节点的校验，等待用户主动触发下一次提交，与"分页填写、逐项提交"的真实业务场景完美匹配。

5. **回退安全可靠** — 按 List 索引回退，被回退的后续节点状态全部重置为 `PENDING`，保证数据一致性，不会出现"回退后遗留了过期校验记录"的问题。
