# STAR 原则逐字稿：企业入驻校验模块设计

> 面试场景：后端开发岗 / 实习转正答辩 / 项目复盘汇报
> 时长约 3~5 分钟（正常语速）
> 定位：**新功能从 0 到 1 设计实现**

---

## S — Situation（背景与需求）

> **时间参考**：2025 年 10 月，我在智园通智慧园区管理平台实习，接到一个新需求——开发企业入驻模块。

智园通是一套面向多种企业类型的数字化管理平台。产品提出了明确的业务需求：企业在线入驻时，不同类型的企业需要走不同的校验流程——科技类需要营业执照加法人信息，金融类多一个金融许可证检查，外资企业还要加涉外资质和投资比例。而且每个校验步骤是分步页面呈现的，用户提交一步才能进入下一步，也支持回退重填。

我们的技术栈是 Spring Boot 加 MyBatis-Plus，部署在集群环境，每个园区部署多个实例。产品明确要求：**校验步骤要可配置、可插拔，不同企业类型的流程差异要能通过数据库配置实现，产品自己就能调整，不需要后端介入**。

---

## T — Task（任务与挑战）

我需要从零设计一个企业入驻校验模块，满足三个核心目标：

1. **可配置**：校验步骤序列存在数据库里，支持按企业类型配置不同的步骤组合和顺序
2. **可插拔**：新增或删除校验项时，只改一个文件，不影响现有流程代码
3. **集群友好**：所有实例行为一致，配置变更不影响进行中的入驻流程，防止重复提交

这三个目标互相制约：灵活配置可能导致代码分散，可插拔可能引入性能问题，集群一致性又增加了复杂度。我需要设计一个平衡的方案。

---

## A — Action（设计与实现）

整个方案分三层实现：**策略层、引擎层、集群一致性层**。

**策略层**：我定义了一个 `ValidationStrategy` 接口，每个校验项比如营业执照、黑名单、金融许可证，都是一个独立的策略类，互不依赖。每个策略只关心自己的校验逻辑。新增一个校验项，只需要新建一个类实现接口，加一条数据库配置，**完全不碰现有代码**。

**引擎层**：我设计了一个 `ValidationEngine`，构造器里做策略一致性预校验——查数据库所有 strategy_id，和代码中的策略映射对比，不匹配直接拒绝启动。真正的策略加载是懒加载：首次用户请求时从 Redis 缓存读取 `validation_config` 表，按企业类型组装成策略列表，每一步用 `List.get(stepOrder - 1)` 直接索引，O(1) 查找。配置变更后 Redis 缓存被清除，下次请求自动重新加载。用户提交第 N 步时，引擎只执行当前步骤的策略，**不自动推进**，符合分步交互的需求。

**集群一致性层**有三个核心设计：

- **快照版本号**：用户开始入驻时，从 `enterprise_config_version` 表读取当前版本号，写入入驻记录。之后管理员改配置，版本号原子递增，新用户读新版本，老用户继续用自己的快照版本，互不干扰。回滚只需把版本号减 1。

- **Redis 分布式缓存**：所有实例共享一份 Redis 缓存，Key 是 `validation_config:{typeId}:{version}`。管理员改配置后删除 Redis Key，所有实例下次加载时自动查库重建。

- **乐观锁加富结果传递**：`EnterpriseRegister` 实体加 `@Version` 注解防止重复提交。引擎的 `executeStep` 返回 `StepExecutionResult` 富结果，把策略标识符和总步数一起传给 Service 层，消除了 submitStep 中对 loadStrategies 的重复调用。

另外加了两个保护机制：启动时的策略一致性校验（数据库 strategy_id 和代码策略实现不匹配直接 Fail-Fast），以及步骤序号的连续性校验（配置错误在加载时就暴露）。

---

## R — Result（结果与价值）

最终模块按期交付，上线后效果很好：

**第一，开发效率高**。校验模块涉及 7 个策略实现、4 张数据表、完整的 CRUD 接口，**代码变更范围控制在合理的模块内**，圈复杂度全部控制在 10 以下。

**第二，业务响应快**。产品给新企业类型配置校验流程、调整现有顺序，直接在后台改数据库就行，**完全不需要后端介入**。上线 3 个月，产品自助调整了 6 次流程，没有找过后端开发。

**第三，集群稳定**。配置变更后，新老用户流程互不影响，**没有出现过生产环境问题**。乐观锁有效防止了重复提交，N+1 查询优化让 5 步校验的数据库调用从 6 次降到了 2 次，接口响应时间下降约 40%。

**第四，技术亮点充足**。从策略模式选型对比、快照版本设计、Redis 集群缓存、乐观锁并发控制，到启动时 Fail-Fast 校验，每个决策都有技术依据，每一个指标都能量化，面试时展开讲 15 分钟没问题。

## 附：关键技术要点速查（面试追问备用）

| 追问方向 | 回答要点 |
|---------|---------|
| 为什么不用责任链？ | 业务语义冲突（自动传递 vs 分步提交）、快照版本死锁、查询性能 O(n) |
| 快照版本怎么实现的？ | 独立版本表 + Redis 缓存 + 入驻时锁定 + 配置变更时原子递增 |
| 集群下配置怎么同步？ | Redis 分布式缓存 + 配置变更时删 Key + 下次加载自动重建 |
| 并发提交怎么控制？ | MyBatis-Plus `@Version` 乐观锁，比分布式锁轻量，适合低冲突场景 |
| 策略标识符为什么不和 Bean Name 绑定？ | 代码重构不影响数据库配置，枚举统一管理 |
| 步骤序号怎么校验？ | 引擎加载时先过滤 enabled，再排序校验连续性 |
| Redis 缓存序列化为什么用 Jackson？ | 可读性好、支持复杂类型、跨语言兼容 |
| 怎么防止配置版本跳变？ | `INSERT ON DUPLICATE KEY UPDATE` 原子操作 |
