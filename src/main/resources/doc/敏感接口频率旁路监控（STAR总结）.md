# 敏感接口频率旁路监控 — STAR 总结

> 本文按 STAR（情境 Situation → 任务 Task → 行动 Action → 结果 Result）原则整理，可直接用于简历项目描述与面试讲解。
> 详细技术设计见同目录《敏感接口频率旁路监控方案.md》（v8 全令牌桶版）。

---

## S（Situation）情境

### 背景

系统中存在查询**敏感信息**的接口（用户资料、订单明细、财务数据、证件信息等），一旦被高频调用，可能引发：

- 敏感数据被**批量拉取**（拖库、爬取），造成数据泄露与合规风险
- 内部账号**越权/被盗用**批量查询客户敏感数据
- 接口资源被异常流量占用，影响正常查询

### 现状与痛点

- 敏感接口**低频但高价值**（正常单账号约 1 次/分钟），一旦异常高频调用，批量拉取可在短时间内造成大量数据泄露
- 缺少频率异常的**观测与告警**能力：无法实时感知"**谁在拉？拉了多少？有多严重？**"
- 异常响应滞后：频率异常没有告警渠道，要等事后翻日志才发现，数据已造成损失

---

## T（Task）任务

设计并实现一套"**敏感接口频率旁路监控**"能力，核心诉求：

- **旁路监控**：不阻断业务，只统计频率 + 超线告警
- **超线异步短信**：独立线程池发送，不占用业务线程
- **冷却降噪**：无效告警降低 99%+
- **故障降级**：Redis 故障时监控链路不中断（断路器 + 本地兜底）
- **多维度防绕过**：账号维度 + 接口级全局水位（防多账号并发批量拉取）
- **低侵入落地**：纯新增组件，对现有系统零侵入、可独立启停

---

## A（Action）行动

方案基于 **AOP 注解 + 切面**实现：在敏感接口方法上标注 `@FrequencyMonitor`（`@Repeatable` 支持多维度叠加），切面在业务方法执行前做一次频率判定，全程只"观测 + 告警"，不阻断业务。

一次请求的判定流程是：切面循环处理方法上叠加的每个监控注解——账号维度用 SpEL 从登录上下文（`#userId`）解析出维度 key（`prefix:account:值`）；注解开启 `globalAlert` 时再额外判定接口全局水位 key（`prefix:global`，独立阈值，防多账号并发批量拉取绕过单账号水位）。判定调用 Redisson `RRateLimiter.tryAcquire()` 做分布式权威判定：有令牌放行、无令牌即超线。`trySetRate` 仅在首次请求配置一次（本地缓存标记），正常流量每请求仅 1 次 Redis 往返（约 1~3ms），超线判定本身不增加额外往返；计数不做——令牌桶不记录总调用次数，接受盲区，不需要精确计数。

判定超线后进入告警链路：用 SET NX EX 原子操作实现冷却判定——冷却期内重复超线被静默，接受冷却期盲区（这是降噪的必然代价），多实例天然去重；短信由独立线程池异步发送，不占用业务线程。

故障时自动降级：Redis 异常（包括故障与桶配置丢失）被宽泛捕获，独立断路器 `monitorRedisCircuitBreaker` 累计失败后熔断，之后 0 延迟切到 Guava 本地令牌桶兜底判定（与主方案同为令牌桶、语义一致），监控链路不中断；同时移除配置标记，Redis 恢复后自动重建桶自愈。整个链路被"旁路铁律"兜底——监控自身任何异常只记日志、绝不污染业务，业务自身异常原样上抛、绝不重放。

### 1. 方案对比与选择（核心决策过程）

#### ① 主判定：Redisson `RRateLimiter` 令牌桶 vs Redis Zset 滑动窗口

- **判定语义**：RRateLimiter 是令牌桶 + 滑动窗口混合——窗口内已消耗会计入、过期自动归还，允许窗口内突发；Zset 是纯窗口计数，元素数随请求增长
- **内存/清理**：RRateLimiter 内部 Zset 记录窗口内请求（紧凑二进制），**每次请求先清理过期并归还令牌，无泄漏**；Zset 每 key 元素 = 窗口内请求数（需自行管理清理与 TTL）
- **精确计数**：RRateLimiter 拿不到精确 → **不计数**，真实严重程度由「状态判断（首次/持续超线）」承载；Zset 直接精确
- **兜底一致性**：RRateLimiter 的 **Guava 同为令牌桶 → 语义完全一致、全现成**；Zset 的本地窗口需自研并发
- **源码可讲**：Redisson / Guava 成熟开源实现，可展开讲内部算法；Zset 需自写 Lua 脚本
- **技术栈一致性**：项目已引入 Redisson/Guava，零新增依赖；Zset 需新引入一套数据模型

**结论**：选 RRateLimiter——项目已引入 Redisson 技术栈、源码可讲、有现成兜底（Guava 同为令牌桶）；滑动窗口"精确计数"的优势被"状态判断（首次/持续超线）"补偿掉，不值得为此自研。

#### ② 兜底：Guava `RateLimiter` vs ArrayDeque/有界队列自研

- **Guava `RateLimiter`（选）**：与主方案**同为令牌桶语义**、全现成、零自研并发；缺点是按秒配桶无窗口计数能力（方案整体不计数，告警靠状态判断承载）
- **ArrayDeque / 有界队列自研**：需自研并发、语义与主方案不一致、面试易被拷打
- **有界队列 + 丢弃**：架构简单，但占业务线程、与主方案语义割裂

**结论**：选 Guava。降级前后判定行为一致（同为令牌桶），是"语义一致性 + 零自研"的最优解。

#### ③ 计数：不计数 vs `availablePermits()` 读水位 vs 自研计数器

- **不计数（选）**：令牌桶不记录总调用次数，超线时读 `availablePermits()` 只会得到"桶空、恒=limit"的冗余值（`tryAcquire()` 返回 false 已确认超线）；只判定、不计数，每请求恒 1 次往返
- **超线时 `availablePermits()` 读水位**：多 1 次往返，信息量却为零（恒=limit），面试易被追问"这个数有什么用"，已否决
- **自研计数器**：多一个组件、面试需解释"为什么不用现成的"，已否决

**结论**：只判定、不计数——`tryAcquire()` 已给出超线事实，砍掉无信息量的水位读取。

#### ④ 告警降噪：SET NX EX + 接受盲区

- **SET NX EX**：Redis 原子占位，冷却期内重复超线被静默，天然多实例去重（无需分布式锁）
- **接受冷却期盲区**：冷却期内的超线信息会丢失，这是降噪的必然代价——敏感接口场景下，持续攻击一定会突破冷却，偶发误操作不需要持续关注
- TTL 到期自动失效，无需手动清理
- 无冷却时 1 小时攻击可产生 **3600 条短信**，冷却 10 分钟后仅 **7 条（-99.8%）**

**结论**：冷却降噪是「有意识的取舍」——接受盲区是降噪的必然代价，简单方案的性价比最高。

#### ⑤ 拦截策略：纯旁路 vs 超线拦截 429

- **纯旁路（选）**：只告警不拦截，业务零打扰；监控与拦截止损解耦，各自独立演进
- **超线返回 429**：监控职责越界（监控不该替业务做决策）；敏感接口误伤正常业务代价高；"联动止损"链路复杂难维护

**结论**：本方案定位"发现 + 通知"，专注观测与告警——拦截属于止损决策，不在本方案职责范围内。

### 2. 整体架构

```
请求 → Controller → Service(标注 @FrequencyMonitor)
                         │
                    ┌────▼─────────────────────────────────┐
                    │ FrequencyMonitorAspect（切面）         │
                    │  1. SpEL 解析 key（Method→表达式缓存）  │
                    │  2. monitor 断路器 OPEN？ ─是──► Guava  │
                    │  3. RRateLimiter.tryAcquire()（主）    │   ← 同步，1 次往返
                    │  4. Redis 异常 → 断路器记失败 → Guava  │
                    │  5. 超线 → 冷却判定 + 异步短信（旁路） │
                    └────┬─────────────────────────────────┘
                         │  proceed() 业务照常执行（旁路）
                         ▼
                    业务逻辑 / 返回 200
```

三层可用性保障：**主方案** Redisson `RRateLimiter` 令牌桶（分布式权威判定）→ **熔断** Resilience4j 独立实例 `monitorRedisCircuitBreaker`（监控链路故障自隔离）→ **兜底** Guava `RateLimiter` 令牌桶（Redis 不可用时本地判定，语义一致）。

### 3. 核心组件与关键实现

- **`@FrequencyMonitor` 注解**（声明监控维度）：`@Repeatable` 支持多维度叠加；`globalAlert` + `globalLimit/globalWindowSeconds` 独立全局水位阈值
- **`FrequencyMonitorAspect` 切面**（旁路判定 + 触发告警）：SpEL key 解析缓存（`ConcurrentHashMap<Method, Expression>`）；`configured` 速率配置缓存（仅首次 `trySetRate`）；`judgeAndAlert` 复用账号/全局判定
- **`AlertCoordinator` 协调器**（冷却 + 异步短信）：SET NX EX 原子占位实现冷却去重，接受冷却期盲区；冷却判定与限流判定共用 `monitorRedisCircuitBreaker` 断路器，实现「一次降级，全局降级」：CLOSED 状态执行 Redis 操作，失败后降级 `ConcurrentHashMap` 本地冷却；OPEN 状态直接走本地兜底（零延迟）
- **`SmsSender` 抽象**（短信通道）：接口 + `LogSmsSender` 日志模拟；实现类自带失败重试（2 次指数退避），可平滑接阿里云/腾讯云
- **`MonitorGuavaLimiterManager`**（兜底限流器）：`ConcurrentHashMap.computeIfAbsent` + 每 10 分钟清理不活跃实例
- **`monitorRedisCircuitBreaker`**（熔断隔离）：独立实例（sliding-window-size=10 / failure-rate 50%），监控链路故障自隔离

### 4. 关键难点与解决

- **旁路语义与同步判定**：**旁路铁律**——监控异常只记日志，绝不污染业务；`proceed()` 移出 try-catch，业务自身异常原样抛出、绝不重放（早期版本二次 proceed 会导致业务执行两次，已修复）
- **令牌桶拿不到精确计数**：只判定、不计数——`tryAcquire()` 返回 false 已确认超线，读 `availablePermits()` 只有"桶空、恒=limit"的冗余值；接受盲区，不需要精确计数
- **冷却 = 接受盲区**：SET NX EX 原子占位实现冷却去重，接受冷却期内的信息丢失——这是降噪的必然代价，敏感接口场景下持续攻击一定会突破冷却
- **多实例重复告警**：SET NX EX 原子操作，天然分布式去重，无需额外分布式锁
- **降级语义一致性**：主/兜底同为令牌桶（Redisson 按窗口配桶 vs Guava 按秒配桶），低频场景差异可忽略
- **Redis 配置丢失自愈**：异常宽泛捕获（`Exception`）+ `configured.remove(key)`，下次请求重新 `trySetRate` 自动恢复
- **多账号并发绕过单账号水位**：账号维度（20 次/分钟）+ 全局水位（500 次/分钟）双保险，独立 key、独立阈值

## R（Result）结果

### 量化效果

- **冷却降噪**：持续超线 1 小时、攻击 60 次/分：告警从 **3600 条 → 7 条（-99.8%）**，达到"无效告警降 99%+"目标
- **监控开销**：正常流量每请求仅 **1 次 Redis 往返（约 1~3ms）**，超线判定不额外增加往返；敏感接口低频场景完全可接受
- **故障零中断**：Redis 故障 → 断路器熔断 → 0 延迟切 Guava 本地判定，告警链路不中断；恢复后半开试探自动切回
- **接受盲区**：冷却期内的超线信息会丢失，但敏感接口场景下持续攻击一定会突破冷却（10分钟后再次超线），不会漏掉持续攻击
- **多维度防绕过**：账号水位 + 全局水位双保险，单账号伪装成多账号批量拉取也能被全局水位捕获

### 业务价值

- 敏感数据批量拉取**分钟级发现**，短信直达运维，形成"发现 → 排查 → 处置"闭环，异常可追溯、可复盘
- **纯新增**组件（`monitor:*` 独立 key 空间、独立断路器实例），对现有系统零侵入、可独立启停

### 技术亮点（面试讲解点）

1. **RRateLimiter 内部三结构**：Hash（rate/interval/type）+ Zset（score=时间戳、value=随机数+令牌数）+ String（剩余令牌），"令牌桶 + 滑动窗口"混合实现，Lua 原子、过期自动清理归还
2. **断路器独立实例**：`monitorRedisCircuitBreaker` 专用监控链路，Redis 故障时自动熔断降级到 Guava 兜底，链路不中断
3. **SET NX EX 原子去重 + 接受盲区**：SET NX EX 原子操作实现冷却去重，天然多实例去重（无需分布式锁）；接受冷却期盲区是降噪的必然代价，敏感接口场景下持续攻击一定会突破冷却
4. **令牌桶语义一致性降级**：Redisson ↔ Guava 同为令牌桶，降级前后判定行为可预期
5. **旁路铁律**：监控异常与业务完全隔离，业务异常绝不重放
