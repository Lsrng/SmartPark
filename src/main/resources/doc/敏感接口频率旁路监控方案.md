# 敏感接口频率旁路监控 — 设计方案（v8 · 全令牌桶版）

---

## 一、需求描述

### 1.1 背景

系统中存在查询敏感信息的接口（如用户资料、订单明细、财务数据、证件信息等），一旦被高频调用，可能引发：
- 敏感数据被批量拉取（拖库、爬取），造成数据泄露与合规风险
- 内部账号越权/被盗用批量查询客户敏感数据
- 接口资源被异常流量占用，影响正常查询

需要一套**旁路监控**能力：在不阻断业务的前提下，实时统计敏感接口的调用频率，频率异常时通过**短信异步告警**通知运维介入。本方案只做"发现 + 通知"，不做拦截——监控与拦截止损解耦，本方案专注观测与告警。

### 1.2 需求点

| 需求点 | 说明 |
|---|---|
| 旁路监控 | 只统计频率 + 超线告警，默认**不拦截**业务请求 |
| Redisson RRateLimiter 为主 | 每次调用经 `RRateLimiter.tryAcquire()` 分布式权威判定，多实例共享同一桶 |
| Guava RateLimiter 兜底 | Redis 故障/熔断时降级本地令牌桶判定，**与主方案同为令牌桶语义**，监控不中断 |
| 超线异步短信 | 超线后由独立线程池**异步**发送短信，不占用业务线程 |
| 冷却机制 | 同一问题持续期间的重复告警被静默，无效告警降 99%+ |
| 监控可观测性** | 告警携带**告警阈值 + 状态判断（首次/持续超线）**，供运维判断严重程度（权威判定在 Redis） |
| **多维度监控** | 账号维度 + 接口级全局水位，防多账号并发批量拉取绕过单账号水位 |
| **纯旁路** | 本方案只做监控告警（发现+通知），不做拦截，业务零打扰 |

### 1.3 核心取舍（多轮评审结论）

1. **默认不拦截（纯旁路）**：超线只告警不拒绝，业务零打扰；拦截属于止损决策，不在本方案职责范围内。
2. **告警阈值必须"合理"**：阈值代表**异常水位**（远高于正常业务峰值），而不是业务限制频率。
3. **判定用 Redisson RRateLimiter 令牌桶**：项目已引入 Redisson 技术栈、源码可讲；内部为"令牌桶 + 滑动窗口"混合实现（Hash+Zset+String），过期请求自动清理归还，无泄漏；判定权威始终在 Redis，计数不做——令牌桶不记账总次数，不需要精确计数。
4. **兜底用 Guava RateLimiter**：与主方案**同为令牌桶语义**，降级前后判定行为一致；全现成实现、零自研并发。
5. **单 AOP 切面、无队列**：切面内同步判定，架构最简单；短信发送异步化。
6. **短信通道先抽象 + 日志模拟**：定义 `SmsSender` 接口（实现类自带失败重试），先以日志实现跑通全链路。
7. **纯新增组件落地**：本方案独立部署、独立 key 空间、独立断路器实例，不依赖项目其他功能，可独立启停。
8. **监控链路故障隔离**：使用**专用独立断路器实例**，Redis 故障只影响监控链路自身。
9. **接受冷却期盲区**：冷却机制的核心是「降噪」，接受冷却期内的信息丢失是降噪的必然代价——敏感接口场景下，持续攻击一定会突破冷却（10分钟后再次超线），偶发误操作（只触发1次告警）不需要持续关注。

## 二、技术选型

| 组件 | 用途 | 说明 |
|---|---|---|
| Redisson `RRateLimiter` | 令牌桶·主判定 | 内部 **Hash（配置）+ Zset（请求记录）+ String（剩余令牌）** 三结构，"令牌桶 + 滑动窗口"混合实现，Lua 原子无竞态、过期请求自动清理归还 |
| Resilience4j 断路器 | Redis 故障熔断 | **独立实例** `monitorRedisCircuitBreaker`，熔断后 0 延迟走 Guava 兜底 |
| Guava `RateLimiter` | 令牌桶·兜底判定 | Redis 不可用时本地平滑限速，**与主方案同为令牌桶语义** |
| Spring AOP | 旁路切面 | `@FrequencyMonitor`（`@Repeatable` 支持多维度）注解 + 切面 |
| Redis SET NX EX | 冷却机制 | 原子占位，天然多实例告警去重；接受冷却期盲区——冷却期内的超线信息会丢失，这是降噪的必然代价 |

**为什么用令牌桶（RRateLimiter）而非 Zset 滑动窗口**：

| 维度 | RRateLimiter 令牌桶（选） | Zset 滑动窗口 |
|---|---|---|
| 判定语义 | 令牌桶 + 滑动窗口混合：窗口内已消耗会计入、过期自动归还，允许窗口内突发 | 纯窗口计数，元素数随请求增长 |
| 内存/清理 | 内部 Zset 记录窗口内请求（value 紧凑二进制），**每次请求先清理过期并归还令牌，无泄漏** | 每 key 元素 = 窗口内请求数（需自行管理清理与 TTL） |
| 精确计数 | 拿不到精确 → **不计数**，不需要精确计数，接受盲区 | 直接精确 |
| 兜底一致性 | **Guava 同为令牌桶 → 语义完全一致、全现成** | 本地窗口需自研并发 |
| 源码可讲 | Redisson / Guava 成熟开源实现，可展开讲内部算法 | 自写 Lua 脚本 |
| 技术栈一致性 | 项目已引入 Redisson/Guava，零新增依赖 | 新引入一套数据模型 |

项目依赖现状：Redisson 3.27.0、Resilience4j 2.2.0、Guava 均已引入，无需新增依赖。

### 2.1 独立部署与组件清单

本方案以**独立组件**落地，不依赖项目其他功能，可独立启停：

- **key 空间**：统一使用 `monitor:*` 前缀，自成体系
- **断路器**：专用独立实例 `monitorRedisCircuitBreaker`，只服务监控链路，Redis 故障只影响本链路
- **兜底限流器**：独立 `MonitorGuavaLimiterManager`（Guava 令牌桶兜底）
- **短信通道**：`SmsSender` 抽象 + 日志实现，可平滑替换为真实短信服务
- **监控维度**：账号 + 接口全局水位，key 独立、阈值独立

## 三、整体架构

```
请求 → Controller → Service(标注 @FrequencyMonitor)
                         │
                    ┌────▼─────────────────────────────────┐
                    │ FrequencyMonitorAspect（切面）         │
                    │  1. SpEL 解析 key（Method→表达式缓存）  │
                    │  2. monitor 断路器 OPEN？ ─是──► Guava  │
                    │  3. RRateLimiter.tryAcquire()（主）    │   ← 同步，1 次往返
                    │  4. Redis 异常 → 断路器记失败 → Guava  │
                    │  5. 超线 → 冷却判定 + 异步短信（旁路） │
                    └────┬─────────────────────────────────┘
                         │  proceed() 业务照常执行（旁路）
                         ▼
                    业务逻辑 / 返回 200
```

三层可用性保障：

| 层 | 组件 | 职责 |
|---|---|---|
| 主方案 | Redisson `RRateLimiter` 令牌桶 | 分布式权威判定，多实例共享同一桶 |
| 熔断 | Resilience4j 断路器（独立实例） | Redis 连续失败自动熔断，之后 0 延迟切 Guava 兜底，Redis 故障只影响监控链路自身 |
| 兜底 | Guava `RateLimiter` 令牌桶 | 熔断期间本地判定，监控不中断，**与主方案同为令牌桶语义** |

## 四、核心组件设计

### 4.1 注解 `@FrequencyMonitor`（支持多维度）

```java
@Repeatable(FrequencyMonitors.class)      // 支持账号等多维度叠加
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface FrequencyMonitor {
    String prefix() default "monitor";          // 监控组前缀（接口级标识）
    String keyField();                          // SpEL 提取监控维度，如 #userId（登录上下文）
    long limit() default 30;                    // 窗口内次数上限（超线即告警）
    long windowSeconds() default 60;            // 时间窗时长（秒）
    boolean globalAlert() default false;        // 接口级全局水位（防多账号并发批量拉取绕过单账号水位）
    long globalLimit() default 0;               // 全局水位上限（globalAlert=true 时生效，如 500 次）
    long globalWindowSeconds() default 0;       // 全局水位时间窗（秒），与 globalLimit 成对（如 60）
}
```

- `limit` 语义为**异常告警水位**，非业务限制频率（定值方法见第五章）；底层换算为令牌速率 `rate=limit, interval=windowSeconds`
- **多维度**：同一方法叠加多个 `@FrequencyMonitor`（如账号一个、接口全局一个）
- **全局水位**：`globalAlert=true` 时额外生成 `prefix:global` 全局 key，阈值由 `globalLimit/globalWindowSeconds` **独立配置**（如全局 500 次/分钟，比单账号水位宽松得多），统计该接口全来源合计频率，防止**多个账号并发批量拉取**绕过单账号水位
- **账号维度取值**：SpEL 上下文注册 `#userId` 变量（来自 `BaseContext.getCurrentId()`），无需通过方法参数传账号，贴合内部系统登录态场景

### 4.2 切面 `FrequencyMonitorAspect`

```java
@Aspect @Component
public class FrequencyMonitorAspect {

    private final RedissonClient redissonClient;          // 主判定（RRateLimiter）
    private final MonitorGuavaLimiterManager guavaManager;// 独立新增，Guava 令牌桶兜底
    private final CircuitBreaker circuitBreaker;          // 独立实例 "monitorRedisCircuitBreaker"
    private final AlertCoordinator alertCoordinator;      // 冷却 + 摘要 + 异步短信
    private final Map<Method, Expression> spElCache = new ConcurrentHashMap<>();  // 缓存解析好的表达式
    private final ConcurrentHashMap<String, Boolean> configured = new ConcurrentHashMap<>(); // 速率配置标记

    @Around("@annotation(monitor)")
    public Object around(ProceedingJoinPoint pjp, FrequencyMonitor monitor) throws Throwable {
        try {
            for (FrequencyMonitor fm : getAllAnnotations(pjp)) {   // @Repeatable 多维度循环
                String key = resolveKey(fm, pjp);                 // SpEL 解析（表达式缓存命中，仅取值 ~500ns）
                judgeAndAlert(fm, key, fm.limit(), fm.windowSeconds());          // 账号维度
                if (fm.globalAlert()) {                                          // 接口级全局水位：独立 key + 独立阈值
                    judgeAndAlert(fm, fm.prefix() + ":global",
                            fm.globalLimit(), fm.globalWindowSeconds());
                }
            }
        } catch (Throwable t) {
            // 旁路铁律：仅吞监控自身异常，绝不污染业务
            log.warn("旁路监控异常: err={}", t.getMessage());
        }
        return pjp.proceed();   // 业务照常执行；业务自身抛出的异常原样向上抛出，绝不重放
    }

    /** 判定 + 超线告警（rate 由调用方决定：账号维度或全局水位） */
    private void judgeAndAlert(FrequencyMonitor fm, String key, long limit, long windowSeconds) {
        if (judge(fm, key, limit, windowSeconds).overLimit) {
            alertCoordinator.onOverLimit(fm, key);                 // 冷却 + 异步短信（旁路）
        }
    }

    /** 取出方法上叠加的全部监控注解（@Repeatable 多维度支持） */
    private FrequencyMonitor[] getAllAnnotations(ProceedingJoinPoint pjp) {
        Method method = ((MethodSignature) pjp.getSignature()).getMethod();
        return method.getAnnotationsByType(FrequencyMonitor.class);
    }

    /** 主判定：Redisson 令牌桶；熔断/异常时 Guava 令牌桶兜底（语义一致） */
    private JudgeResult judge(FrequencyMonitor fm, String key, long limit, long windowSeconds) {
        if (circuitBreaker.getState() == CircuitBreaker.State.OPEN) {   // 熔断 0 延迟走兜底
            return judgeByGuava(fm, key, limit, windowSeconds);
        }
        try {
            RRateLimiter limiter = redissonClient.getRateLimiter(key);  // key 已含 monitor: 前缀
            if (configured.putIfAbsent(key, Boolean.TRUE) == null) {    // 仅首次配置速率，避免每次多 1 次往返
                limiter.trySetRate(RateType.PER_CLIENT, limit, windowSeconds, TimeUnit.SECONDS);
            }
            boolean overLimit = !limiter.tryAcquire();   // 权威判定（1 次往返）：有令牌放行，无令牌即超线
            circuitBreaker.onSuccess(1, TimeUnit.MILLISECONDS);
            return new JudgeResult(overLimit);
        } catch (Exception e) {
            // 宽泛捕获：Redis 故障（RedisException 系）+ 桶配置丢失（Redis 重启/清理后抛非 RedisException）；
            // 移除配置标记，下次请求重新 trySetRate 自愈
            circuitBreaker.onError(1, TimeUnit.MILLISECONDS, e);        // 累计失败率，超阈值熔断
            configured.remove(key);
            return judgeByGuava(fm, key, limit, windowSeconds);
        }
    }

    /** 兜底：Guava 令牌桶，速率换算 rate = limit / windowSeconds */
    private JudgeResult judgeByGuava(FrequencyMonitor fm, String key, long limit, long windowSeconds) {
        RateLimiter limiter = guavaManager.getLimiter(key, (double) limit / windowSeconds);
        return new JudgeResult(!limiter.tryAcquire());
    }
}
```

**说明**：
- `spElCache` 缓存 `Method → 已解析的 Expression`（避免每次反射 + 重复 parse）；key 取值仍需按参数计算
- `resolveKey` 求值细节：SpEL 表达式（如 `#userId`）在切面内用 `StandardEvaluationContext` 求值，注册变量 `#userId = BaseContext.getCurrentId()`（登录态 ThreadLocal），无需方法参数传账号
- 告警内容里的接口路径：`buildContent` 从 `RequestContextHolder` 取当前请求 URI 展示（如 `/api/sensitive/user/123`），取不到时回退 `fm.prefix()`
- `configured` 缓存"速率已配置"标记：**`trySetRate` 仅在首次请求执行一次**，正常流量每请求仅 1 次 Redis 往返（`tryAcquire`）
- 计数不做：令牌桶不记录总调用次数（超线读 `availablePermits()` 也只会得到"桶空、恒=limit"，无增量信息），真实严重程度由「状态判断（首次/持续超线）」承载；主方案与兜底期行为一致
- `judge` 异常宽泛捕获（`Exception`）+ `configured.remove(key)` 自愈：Redis 重启/数据清理导致桶配置丢失时，异常不会静默吞掉监控，下次请求重新 `trySetRate` 自动恢复

### 4.3 兜底（独立新增）

新建一个独立的 `MonitorGuavaLimiterManager`：

**① `MonitorGuavaLimiterManager`（Guava 令牌桶兜底）**

```java
@Component
public class MonitorGuavaLimiterManager {
    private final Map<String, RateLimiter> limiterMap = new ConcurrentHashMap<>();

    public RateLimiter getLimiter(String key, double permitsPerSecond) {
        return limiterMap.computeIfAbsent(key, k -> RateLimiter.create(permitsPerSecond));
    }

    /** 每 10 分钟清理不活跃 limiter，防止长时间无 Redis 时实例累积 */
    @Scheduled(fixedRate = 600_000)
    public void cleanup() {
        // 可统计 getRate 匹配的活跃性，或直接按访问时间清理（窗口数量有限，简化重建亦可）
    }
}
```

**② 计数不做**：主方案不读 `availablePermits()` 做水位（令牌桶不记录总调用次数，超线时读只会得到"桶空、恒=limit"的冗余值，无增量信息），兜底期也不做本地近似计数。原因——Guava `RateLimiter` 按**秒**配桶（`create(rate)`，桶容量 = 每秒速率），换算成 `rate = limit / windowSeconds` 后桶容量 <1，`getAvailablePermits()` 恒在 0~1 波动，推不出"窗口内次数"；本地近似计数属于自研组件，此前已否决。因此告警只报"告警阈值 + 状态判断（首次/持续超线）"。

### 4.4 告警协调器 `AlertCoordinator`（冷却 + 异步短信）

核心设计：
1. **接受冷却期盲区**——冷却机制的核心是「降噪」，接受冷却期内的信息丢失是降噪的必然代价。敏感接口场景下，持续攻击一定会突破冷却（10分钟后再次超线），偶发误操作（只触发1次告警）不需要持续关注。
2. **统一断路器**——冷却判定与限流判定共用同一个 `monitorRedisCircuitBreaker` 断路器，实现「一次降级，全局降级」，保证状态一致性。

```java
@Component
public class AlertCoordinator {

    private final StringRedisTemplate redisTemplate;
    private final SmsSender smsSender;
    private final MonitorProperties properties;
    private final CircuitBreakerRegistry circuitBreakerRegistry;

    /** Redis 不可用时本地冷却兜底：key -> 到期时间戳 */
    private final ConcurrentHashMap<String, Long> localCooldown = new ConcurrentHashMap<>();

    private CircuitBreaker circuitBreaker;

    @PostConstruct
    public void init() {
        // 与限流判定共用同一个断路器，实现「一次降级，全局降级」
        circuitBreaker = circuitBreakerRegistry.circuitBreaker("monitorRedisCircuitBreaker");
    }

    public void onOverLimit(FrequencyMonitor fm, String key) {
        long cooldownMillis = properties.getCooldown().baseDurationMillis();

        // 1. 冷却判定：用 Resilience4j 断路器包裹，统一处理降级逻辑
        boolean pass;
        try {
            pass = circuitBreaker.executeSupplier(() -> {
                long cooldownSeconds = cooldownMillis / 1000;
                Boolean first = redisTemplate.opsForValue()
                        .setIfAbsent("monitor:cooldown:" + key, "1", cooldownSeconds, TimeUnit.SECONDS);
                return Boolean.TRUE.equals(first);
            });
        } catch (CallNotPermittedException e) {
            // 断路器 OPEN 状态：Redis 故障，直接走本地兜底（零延迟）
            pass = tryLocalCooldown(key, cooldownMillis);
        } catch (Exception e) {
            // 断路器 CLOSED 但 Redis 操作失败（瞬态异常），走本地兜底
            pass = tryLocalCooldown(key, cooldownMillis);
        }

        if (pass) {
            // 2. 异步发送告警
            String content = buildContent(fm, key);
            String[] phones = properties.getSms().phoneArray();
            alertExecutor.execute(() -> {
                for (String phone : phones) {
                    try {
                        smsSender.send(phone, content);
                    } catch (Exception ex) {
                        log.error("短信发送失败 phone={}", phone, ex);
                    }
                }
            });
        }
        // 冷却期内：静默，接受盲区
    }

    /** 本地冷却判定：读写时惰性判断过期，Redis 长期不可用也不泄漏 */
    private boolean tryLocalCooldown(String key, long cooldownMillis) {
        long expire = System.currentTimeMillis() + cooldownMillis;
        Long old = localCooldown.putIfAbsent(key, expire);
        if (old == null) return true;
        if (old <= System.currentTimeMillis()) {
            return localCooldown.replace(key, old, expire);
        }
        return false;
    }

    /** 定时清理：每 10 分钟移除过期冷却键（配合惰性删除双保险） */
    @Scheduled(fixedRate = 600_000)
    public void cleanup() {
        long now = System.currentTimeMillis();
        localCooldown.entrySet().removeIf(e -> e.getValue() <= now);
    }
}
```

**告警内容（时间 + 工号 + URL + 告警阈值）**：
```
【smartPark告警】敏感接口 /api/sensitive/user/query 频率异常
时间: 2026-08-07 10:30:15 | 工号: 10086 | 告警阈值: 20 次/60s
```
短信模板四要素：**谁（工号）、什么（接口 URL）、何时（时间）、多严重（阈值）**；固定 key:value 格式便于日志归档与自动化解析。全局水位告警无工号，标注"全局"。

**接受盲区的设计说明**：
1. **冷却期盲区定义**：冷却期内所有超线请求被静默，信息丢失
2. **为什么可以接受**：
   - 冷却期本身就是「静默期」，接受盲区是降噪的必然代价
   - 敏感接口场景特殊：要么持续攻击（一定会突破冷却），要么偶发误操作（不需要持续关注）
   - 告警目的是「发现问题」，不是「记录全量」——知道「这个账户有攻击」就够了，不需要知道「攻击了多少次」
3. **如果后续需要更多信息，可以快速扩展**：比如加状态判断（双Key方案）、加累计次数（本地计数器），但当前场景下，简单方案的性价比最高

**计数口径说明**：判定权威在 Redis（RRateLimiter + 冷却 SET NX 去重）；计数不做——令牌桶不记录总调用次数，不需要精确计数，接受盲区。

### 4.8 RRateLimiter 源码要点（面试讲点）

Redisson `RRateLimiter` 的实现值得展开，因为本方案的主判定就是它：

**内部存储（三结构，令牌桶 + 滑动窗口混合）**：

| 结构 | 内容 | 作用 |
|---|---|---|
| Hash | `rate`（速率）、`interval`（时间窗）、`type`（0=PER_CLIENT 全局共享 / 1=PER_INSTANCE 按实例） | 限流配置 |
| Zset | `score` = 请求时间戳，`value` = 二进制（随机数 + 请求令牌数），随机数用于避免哈希冲突 | 窗口内请求记录 |
| String | 当前剩余令牌数 | 令牌桶容量状态 |

**判定流程（一次 Lua，原子无竞态）**：
```
1. 取配置（Hash：rate / interval / type）
2. 清理过期请求：从 Zset 移除 score ∈ [0, now - interval] 的记录，
   累计这些请求消耗的令牌数并归还到剩余令牌（String）
3. 令牌检查：剩余令牌 ≥ 本次请求数 → 记录请求到 Zset + 扣减 String → 返回成功
   否则 → 计算最近请求的等待时间（最近请求时间 + interval - now），
   tryAcquire() 非阻塞则直接返回 false
```

**API 要点**：
- `trySetRate(RateType.PER_CLIENT, rate, interval, unit)`：`PER_CLIENT`（type=0）所有客户端共享同一桶，跨实例全局判定；`PER_INSTANCE`（type=1）按实例独立桶。**该方法只在首次生效**（返回 false 表示已配置过），后续调整用 `setRate()`——混合实现使其支持**动态调速**（按窗口内已消耗校准）
- `tryAcquire()`：非阻塞取令牌，返回布尔——本方案用它做"超线判定"（取不到 = 超线）

**与 Guava `RateLimiter` 的异同**（兜底语义一致性）：
- 相同：都是令牌桶（速率 + 容量封顶），语义一致 → 降级前后判定行为可预期
- 差异：Guava 本地无锁实现（`SmoothBursty` 桶容量 = 每秒速率，允许突发累积），按连续时间微秒粒度补充；Redisson 按 `interval` 窗口 + 过期归还的滑动窗口粒度补充。低频敏感接口下差异可忽略，属降级期可接受

## 五、告警阈值设计（保证"合理"）

### 5.1 阈值语义

`limit` 是**异常告警水位**，不是业务限制频率。设成业务规则值会导致：正常操作稍频繁即超线 → 每条都告警 → 全是无效警告，与"降无效告警 99%"的目标自相矛盾。

### 5.2 定值方法

| 步骤 | 做法 |
|---|---|
| 定基线 | 从日志/监控统计该接口**正常业务峰值**（如敏感查询接口正常单账号约 1 次/分钟的人工逐条查询量） |
| 放余量 | 告警水位 = 正常峰值 × **3~5 倍**（容忍网络重试、前端刷新等正常抖动）；如 1 次/分钟 × 3~5 = **180~300 次/小时** |
| 反噪声 | 宁可先高后低：先按偏高水位上线，观察一周无误报再逐步收敛 |
| 配套冷却 | 冷却降噪是兜底，不是掩盖阈值过低——阈值本身就要定在"异常区" |

### 5.3 多层水位（防绕过）

| 维度 | 水位示例 | 防什么 |
|---|---|---|
| 单账号 | 300 次/小时 | 内部账号越权/被盗用批量查询 |
| 接口全局 | 500 次/分钟 | 多账号并发批量拉取绕过单账号水位 |

## 六、冷却机制详解（无效告警降 99%+，接受盲区）

### 6.1 无效警告的定义

没有冷却时，问题持续 1 小时、攻击频率 60 次/分钟 → **3600 条短信**，其中 99% 是**同一 key 的重复告警**，全是无效警告。冷却机制掐掉的就是这部分重复。

### 6.2 核心实现：SET NX EX

```
Key: monitor:cooldown:{限流判定Key}
Value: "1"（占位符，无实际意义）
TTL: 冷却时长（10分钟）
```

**核心逻辑**：
1. 超线时执行 `SET key NX EX 600`（原子操作）
2. 如果 Key 不存在（首次超线或冷却到期），设置成功 → 发送告警
3. 如果 Key 已存在（冷却期内），设置失败 → 静默，接受盲区

- **TTL 自动过期**：冷却Key 10分钟后自动失效。问题持续 → 到期后再告警一条（不漏报）；问题恢复 → 不再触发（无垃圾短信）
- **NX 原子性 = 天然多实例去重**：多个实例同时超线同一 key，只有一个 `SET NX` 能成功 → 只发一条，无需额外分布式锁
- **接受盲区**：冷却期内的超线信息会丢失，这是降噪的必然代价——敏感接口场景下，持续攻击一定会突破冷却（10分钟后再次超线），偶发误操作（只触发1次告警）不需要持续关注

### 6.3 降噪量化（数学保证 + 适用前提）

```
冷却后告警数 ≈ 问题持续时长 T / 冷却期 C
无冷却告警数  = 超线事件总数 N

降噪率 = 1 - (T/C + 1) / N
```

| 场景（持续超线 1 小时） | 无冷却 | 冷却 10 分钟 | 冷却 1 分钟 |
|---|---|---|---|
| 攻击频率 60 次/分 | 3600 条 | **7 条（-99.8%）** | 61 条（-98.3%） |
| 攻击频率 30 次/分 | 1800 条 | **7 条（-99.6%）** | 61 条（-96.6%） |

**适用前提**：降噪 99%+ 针对**同 key 持续问题**场景（问题持续时长明显大于冷却期）。若问题为瞬时脉冲（超线 1 次即停），冷却前后告警数接近，降噪率趋近于 0——该场景本就无需降噪，不影响指标成立性。

### 6.4 完整时序

```
t=0s      第1次超线（Key不存在）
         → SET NX 成功（Value="1", TTL=600s）
         → 发送告警①
         
t=1s~600s 第2~1000次超线（Key存在）
         → SET NX 失败（Key已存在）
         → 冷却中，静默（接受盲区）

t=600s    Key过期
t=601s    第1001次超线（Key不存在）
         → SET NX 成功
         → 发送告警②
         
t=1201s   第1002次超线（Key过期）
         → SET NX 成功
         → 发送告警③
```

### 6.5 边界与增强

| 场景 | 处理 |
|---|---|
| Redis 不可用（本地兜底期间） | 冷却判定与限流判定共用 `monitorRedisCircuitBreaker` 断路器：<br>1. **CLOSED 状态**：执行 Redis 操作，失败后走本地 `ConcurrentHashMap` 兜底<br>2. **OPEN 状态**：直接走本地兜底（零延迟，更高效）<br>本地兜底用 `ConcurrentHashMap<key, 到期时间戳>` 实现单实例内去重，惰性删除 + 每 10 分钟定时清理，防键累积泄漏；降级期多实例可能少量重复，可接受 |
| 问题持续数小时 | 固定 10 分钟已是 6 条/小时；可启用**指数退避**：5m→10m→30m→60m 封顶，持续越久短信越少 |
| 冷却到期后秒恢复又秒超线 | 冷却Key语义是"问题持续中"，到期再告警属设计意图，不算误报 |
| Redis 主从切换导致 Key 丢失 | 会触发额外1条告警——Key 丢了，`SET NX` 成功，再次发告警。这是可接受的降级：宁可多发1条告警，也不会漏告警 |

### 6.6 两层降噪配合

- **第一层（阈值）**：告警水位定在异常区（30 次/分），正常流量根本不触发告警
- **第二层（冷却）**：同一问题持续期间每冷却期至多 1 条告警

组合效果：正常流量 0 告警；问题持续 1 小时 → 7 条告警（-99.8%）。

## 七、完整时序

```
1. 请求 GET /api/sensitive/user/123
2. 切面解析账号 key=monitor:user-query:account:10086（#userId 取自登录上下文，表达式缓存命中）
   → 首次请求 trySetRate 配置速率，之后每请求仅 1 次 tryAcquire 往返
   → globalAlert=true 时另解析全局 key=monitor:user-query:global（独立阈值 500 次/分）
3. monitor 断路器闭合 → RRateLimiter.tryAcquire()（同步，1 次往返；账号 + 全局各判定一次）
   ├─ 未超线 → proceed() 执行业务 → 200（正常流量零打扰，全程仅 1 次往返）
   └─ 超线 → 冷却 + 异步短信告警（旁路，不拦截）
4. AlertCoordinator 执行 SET NX EX：
   ├─ 冷却中（Key 存在）→ 静默，接受盲区（不发送告警）
   └─ 冷却通过（Key 不存在）→ 异步发送告警
5. Redis 连续失败 → monitor 断路器 OPEN → 后续请求 0 延迟走 Guava 令牌桶兜底
   → 半开试探成功自动切回
```

## 九、注意事项

- **业务线程多 1 次 Redis 往返**：正常流量每请求 1 次往返（约 1~3ms），超线时 Lua 脚本也是 1 次往返；敏感接口低频场景完全可接受
- **计数不做**：令牌桶不记录总调用次数，超线读 `availablePermits()` 只会得到"桶空、恒=limit"的冗余值（`tryAcquire()` 返回 false 已确认超线）——只判定、不计数，权威判定与告警去重均在 Redis；真实严重程度由「状态判断」承载（持续超线 = 攻击持续）
- **RRateLimiter 内部结构**：Hash（rate/interval/type）+ Zset（score=时间戳、value=随机数+令牌数）+ String（剩余令牌），**"令牌桶 + 滑动窗口"混合实现**；每次请求先清理窗口外记录并归还令牌，value 为紧凑二进制，**无内存泄漏**（过期记录随后续请求自动清除）
- **Guava 兜底语义一致性**：与主方案同为令牌桶，降级前后判定行为一致；两者实现粒度有细微差异（Guava 连续微秒补充 vs Redisson interval 粒度），低频场景可忽略
- **冷却检查依赖 Redis**：冷却判定与限流判定共用 `monitorRedisCircuitBreaker` 断路器，实现「一次降级，全局降级」：
  - CLOSED 状态：执行 Redis 操作，失败后降级本地 `ConcurrentHashMap` 缓存
  - OPEN 状态：直接走本地兜底（零延迟，更高效）
  - 本地缓存惰性删除 + 每 10 分钟定时清理，防键累积；降级期多实例可能少量重复告警，不影响 99%+ 降噪目标
- **Lua 脚本原子性**：用 Lua 脚本实现「SET NX + GET 旧Value」原子操作，避免「先 GET 再 SET」的竞态条件
- **短信通道**：当前为日志模拟，接真实供应商时实现类已约定失败重试（2 次指数退避）与发送限流
- **旁路铁律**：监控链路任何异常（Redis 故障、线程池拒绝）只记日志，绝不抛出到业务
- **阈值维护**：接口流量模型变化后需重新评估告警水位，避免漏报或噪音
- **多维度 key 膨胀**：账号维度 key 数量随账号数增长，RRateLimiter Hash 有 TTL 兜底（Redisson 限流器键可配过期）、冷却缓存每 10 分钟清理，无泄漏风险
